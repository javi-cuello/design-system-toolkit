# Knowledge

What the toolkit knows about doing the work well, past what any run has proven: fundamentals, patterns, cases and practice, each with its public sources. What it may hold, and how it is read, is [toolkit-standard §D 21](../standards/toolkit-standard.md#21--knowledge-is-guidance-with-sources-never-rules): guidance, never rules, each page citing a standard's rule by handle rather than restating it. Any new UI work starts from the pages for what it builds, before its first line; in a project the edit hook names them and the push refuses an interface commit without a `Knowledge:` trailer.

Each topic or pattern section follows one shape: use when or what good looks like, how, cases, accessibility, **build** (the code counterpart: elements, ARIA and keyboard model, states as attributes, the code-standard rules it serves, linking the `code/` section that owns the detail), check (what a script can measure, what a reviewer asks), and sources; where sources disagree the item is `contested` and names each side, and the project decides (a toolkit convention is a standard's rule, which the page cites: toolkit-standard §D 21). A pattern page holds what spans components (choosing between them, how they combine); a component's own guidance lives on its component page, which the pattern page it came from links. Every component page has one shape, checked by `check-standards`: an intro naming what it owns and what stays in which pattern page; **Overview** (*Use when / don't use*, *Anatomy*); its topic sections, each in the section shape above; **In Figma** (*Layers*, *Properties*, *Variants and states*, *Tokens*, *Check*, *Sources*), citing figma-standard's rules; **Alignment with code** (*Structure*: how code splits the component, and the Figma components that mirror it; *Mapping*: each Figma axis and property to its prop, attribute or pseudo-class; *States*: which the browser sets, which a prop sets, and the combinations code cannot reach; *Differences*: where the Figma build departs from the code on purpose, and why; *Check*; *Sources*); and **In code** (*Element*, *Props*, *Check*, *Sources*). [`ui/components/button.md`](ui/components/button.md) is the model. Text field, card and the components with no section of their own yet are written when work first needs them. A design pattern never ships without its build part, and a code page that implements a ui pattern names it in an **Implements:** line under its intro; a code page's own sections are the build, so they carry no build part. The `frontend-build` skill walks these pages when it builds or audits.

## Weights

The pages hold evidence and how-to, never opinion: a spec, shipped source, a tool's documented or tested behaviour, what shipping systems do. A rule is a standard's, a project's truth is its own, and the toolkit's reasoning is not admitted. Every item on a page opens with a weight, `[required]`, `[strong]`, `[moderate]`, `[weak]` or `[contested]`, so a reader knows how far to lean on it. A `[weak]` item rests on one source: it is the research queue, and no reader acts on it. What each weight means, what moves an item along the scale, what each asks of an agent and which lines carry none are [toolkit-standard §D 21](../standards/toolkit-standard.md#21--knowledge-is-guidance-with-sources-never-rules)'s alone; `check-standards` refuses an item with no weight. When a source is added, checked or contradicted, the item's weight moves in the same change.
