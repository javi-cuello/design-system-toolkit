# Internationalisation and right-to-left

How a front end is built so it can be read in another language, script and direction without a rewrite: the document's language and direction, logical properties, bidirectional text, locale-aware formatting with `Intl`, room for longer text, strings a translator can work with, sorting, and fonts that cover the script. It serves the design-standard principles *for everyone, in any context* and *consistent, not uniform*, and applies code-standard rule 54 (rem lengths that follow the reader), code-standard rule 57 (a size derived from content, never fitted to today's words) and code-standard rule 35 (a check pins its locale). No code-standard rule is admitted for internationalisation yet; logical properties wait in [candidates](candidates.md). Wording itself is [content](../ui/design/content.md); layout across widths is [responsive](responsive.md).

## Language and direction

**What good looks like**
- `<html lang>` names the page's language, and any passage in another language carries its own `lang`.
- `dir` is set in markup on `<html>`, and on an element only where the base direction really changes.
- Direction never comes from CSS `direction`.

**How**
- Set both on the root: `<html lang="ar" dir="rtl">`. The W3C advice is to put `dir` on the `html` tag and "Never use CSS to apply the base direction" ([W3C, *Structural markup and right-to-left text*](https://www.w3.org/International/questions/qa-html-dir)), because direction is content, and CSS can be stripped or overridden.
- Use a language tag a browser and screen reader recognise (BCP 47: `en-GB`, `pt-BR`, `zh-Hant`). The tag selects the screen-reader voice, hyphenation, spell checking and the font fallback for Han characters ([W3C, *Why use the language attribute?*](https://www.w3.org/International/questions/qa-lang-why)).
- Style off direction with `:dir(rtl)` rather than `[dir="rtl"]`: the pseudo-class matches the inherited direction, the attribute selector only the element that carries it ([MDN `:dir()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:dir)).
- Server-rendered pages take `lang` and `dir` from the same locale setting that chooses the strings, so the two cannot disagree.

**Cases**
- A quotation in French inside an English article → `<blockquote lang="fr">`; without it a screen reader reads French with English phonetics.
- A theme toggle writes `direction: rtl` on `body` for the Arabic build → move it to `dir="rtl"` on `<html>`; the attribute holds without the stylesheet, and W3C notes it also sets the direction of attribute text such as `alt` and of overflow.
- An icon component flips its arrow with `[dir="rtl"] &` → `:dir(rtl)`; a component inside a `dir="ltr"` island (a code sample) should not flip, and only the pseudo-class knows.

**Accessibility**
- WCAG 2.2 3.1.1 Language of Page (A) and 3.1.2 Language of Parts (AA). The page language is also what code-standard rule 1's "markup stands on its own" reads first.

**Check**
- *Script:* could, in `tools/parity/pages.mjs` structure: assert `<html>` has a non-empty `lang` and, where the language is right-to-left, `dir="rtl"`; flag any `direction:` declaration in a component sheet.
- *Judgement:* Does every passage in a second language say so?

**Sources:** W3C Internationalization as linked; [MDN `lang`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/lang) and [MDN `dir`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/dir). The sources agree.

## Logical properties and mirroring

**What good looks like**
- Spacing, borders, insets and alignment are written in flow-relative terms (`inline`, `block`, `start`, `end`), so a change of direction mirrors the layout with no second stylesheet.
- What must not mirror (a media player's controls, a clock, a chart's time axis, a brand mark) is decided and said, not left to chance.
- Directional icons (back, forward, a chevron in a list item) mirror; icons of real objects do not.

**How**
- Write `margin-inline-start`, `padding-inline`, `inset-inline-end`, `border-inline-start`, `text-align: start`, `inline-size` and `block-size` in place of their physical equivalents ([MDN, *Logical properties and values*](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Logical_properties_and_values)). Flexbox and grid already follow the inline direction.
- `text-align: start` rather than `left`; `start` is also the initial value, so most rules need nothing ([MDN `text-align`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-align)).
- Mirror a directional icon with a transform keyed on direction, once, in the icon component:

  ```css
  :where(:dir(rtl)) [data-icon-flip] { transform: scaleX(-1); }
  ```

- Physical properties remain right where the meaning is physical: a shadow cast by a light from the top left, a gradient tied to an image.

**Cases**
- A list item has `padding-left: 1rem` for its bullet → `padding-inline-start`; in Hebrew the bullet sits on the right and the padding must follow it.
- A "Next" button carries a right-pointing arrow → mark the icon to flip; in a right-to-left reading, forward is to the left.
- A progress bar fills left to right → let it follow the inline direction; a timeline of dates in a chart may stay left to right if the design says so, which is a decision to record.
- A design file draws only the left-to-right layout → build with logical properties anyway and check the mirrored page; the design not drawing it is not a reason to hard-code it ([figma-handoff](figma-handoff.md)).

**Accessibility**
- 1.3.2 Meaningful Sequence: mirroring keeps reading order and visual order aligned in both directions (code-standard rule 2).

**Check**
- *Script:* could flag physical properties (`margin-left`, `padding-right`, `left:`, `text-align: left`) in component sheets, and render each page with `dir="rtl"` under `tools/parity/pages.mjs` overflow to find what breaks.
- *Judgement:* Of what stays physical, is each one physical in meaning?

**Sources:** MDN and W3C as linked. The toolkit goes with logical properties by default; the case for them is in [candidates](candidates.md) until an incident proves it.

## Bidirectional text

**What good looks like**
- Text whose direction is unknown when the page is written (a user name, a search term, a product title) is isolated, so it cannot reorder the punctuation and numbers around it.
- Isolation uses markup, not Unicode control characters typed into strings.

**How**
- `dir="auto"` on an element that tightly wraps the inserted text: the browser takes the direction from its first strong character ([W3C, *Inline markup and bidirectional text*](https://www.w3.org/International/articles/inline-bidi-markup/)).
- `<bdi>` where there is no wrapping element: it isolates its content and defaults to `dir="auto"` ([MDN `<bdi>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/bdi)).
- Form fields that accept free text take `dir="auto"` too, so a person typing Arabic into an English form sees it right to left.

  ```html
  <li><bdi>${name}</bdi>: ${count} reviews</li>
  <input type="search" name="q" dir="auto">
  ```

**Cases**
- A list reads "פיצה סגלה - 5 reviews" with the count jumping to the wrong side → wrap the name in `<bdi>`; W3C's own example is this exact shape.
- A table cell shows an email address in a right-to-left page and the `@` moves → `dir="ltr"` on the cell's content; an address, a URL and a phone number are left-to-right whatever the page.
- A translator adds U+202B (RLE) to a string to fix a display → remove it and isolate in markup; control characters are invisible in review and survive into copied text.

**Accessibility**
- 1.3.2 Meaningful Sequence: a reordered run changes what is read. 3.1.2 Language of Parts where the isolated text is also another language.

**Check**
- *Script:* could flag interpolated text in templates that sits in no element with `dir`, and bidi control characters (U+202A to U+202E, U+2066 to U+2069) in string files.
- *Judgement:* Which inserted values could arrive in either direction?

**Sources:** W3C and MDN as linked; they agree.

## Numbers, dates, plurals and lists

**What good looks like**
- Every number, date, time, currency, relative time, plural and list a person reads is formatted by `Intl` for the page's locale, never assembled by hand.
- The locale comes from one place (the same setting that sets `lang`), and the time zone is stated where it matters.

**How**
- [`Intl`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl) covers them: [`NumberFormat`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat) (grouping, decimals, currency, units, `notation: "compact"`), [`DateTimeFormat`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat), [`RelativeTimeFormat`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/RelativeTimeFormat), [`PluralRules`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/PluralRules) and [`ListFormat`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/ListFormat).
- Plurals take a category, not a number: languages use up to six (`zero`, `one`, `two`, `few`, `many`, `other`), and English uses two (MDN `PluralRules`). Strings are keyed by category.

  ```js
  const lang = document.documentElement.lang;
  const n = new Intl.NumberFormat(lang).format(1234.5);     // "1,234.5" / "1.234,5"
  const cat = new Intl.PluralRules(lang).select(count);     // "one", "few", …
  const list = new Intl.ListFormat(lang).format(names);     // "A, B and C"
  ```

- Machine-readable values stay machine-readable: `<time datetime="2026-10-11">` with the formatted date as its text; `<data value="1234.5">` for a number.
- Create a formatter once per locale and reuse it; constructing one per call in a long list is measurable.

**Cases**
- A count reads `count + " item" + (count === 1 ? "" : "s")` → `PluralRules` with one string per category; the ternary is wrong in Polish, Arabic and Welsh.
- A date is rendered `day/month/year` by string concatenation → `DateTimeFormat` with `dateStyle`; an American reader takes 03/04 as March.
- A server renders "2 hours ago" in its own time zone and the page is cached → render the `<time datetime>` and format relative time in the browser, or state the zone.
- A check passes on one machine and fails on another because a number formats differently → the check pins its locale and time zone (code-standard rule 35).

**Accessibility**
- 3.1.1 and 3.1.2: formatted values follow the page language, so a screen reader reads them in the right voice. A `<time>` with `datetime` gives assistive technology and machines the exact value.

**Check**
- *Script:* could flag string concatenation around a number in templates (`+ "s"`, `count === 1`), `toFixed` on displayed values, and hand-built date strings.
- *Judgement:* Does every value a reader sees go through one locale?

**Sources:** MDN as linked; the ECMAScript Internationalization API is the one standard here, so nothing disagrees.

## Text expansion and no fixed widths on text

**What good looks like**
- Every box that holds text grows with it: buttons, tabs, table columns, badges and labels wrap or grow, and none is sized to today's English.
- Layout is tested with long strings, not with the copy in the design file.

**How**
- Expect expansion, and most of it in short strings. IBM's averages, quoted by W3C: up to 10 characters, 200 to 300%; 11 to 20, 180 to 200%; over 70, 130% ([W3C, *Text size in translation*](https://www.w3.org/International/articles/article-text-size)). Chinese, Japanese and Korean text is shorter in characters but each glyph is wider.
- Size from content, as [responsive: intrinsic layout first](responsive.md#intrinsic-layout-first) sets out (code-standard rule 57); `rem` for anything a design gives (code-standard rule 54).
- Let text wrap before truncating it; where truncation is unavoidable, the full text is reachable (a title, a tooltip, the detail page).
- Pseudo-localise: replace each string with an accented, 40% longer version (`[Ŝéàŕçĥ ƒîļţéŕš ·····]`) and run the overflow gate against it.

**Cases**
- A segmented control fits four English words at 320px → render it pseudo-localised; if it no longer fits, it wraps or becomes a menu, which is a design decision ([selection](../ui/patterns/selection.md)).
- A button with `height: 40px` clips a second line in Finnish → `min-block-size` and padding; the height is the design's minimum, not a cap.
- A heading truncated with an ellipsis at one line → allow two lines first; truncation hides exactly the words a translator added to be clear.

**Accessibility**
- 1.4.4 Resize Text, 1.4.10 Reflow and 1.4.12 Text Spacing: a layout that survives translation also survives a reader's larger text and wider spacing, for the same reason.

**Check**
- *Script:* `tools/parity/pages.mjs` overflow measures a child drawn outside its parent at several widths; run it on a pseudo-localised build as well as the real one. `tools/css-lint` "literal is a token" catches a length that should have been a token, not one that should have been none.
- *Judgement:* Which box would break if its words doubled?

**Sources:** W3C as linked. The toolkit adds pseudo-localisation as practice (commentary); no primary source prescribes a percentage.

## Strings a translator can work with

**What good looks like**
- Each sentence is one string with named placeholders, so a translator can reorder it.
- No user-facing text lives in images, CSS `content`, or code that builds a sentence from parts.
- Strings are keyed, every key is used, and the words come from the locale, not from a story or a fixture.

**How**
- One message per sentence, with placeholders: `"{name} invited you to {project}"`, not `"" + name + " invited you to " + project`. Word order differs between languages; a fragment cannot move.
- Plurals and gender as message variants (ICU MessageFormat or the library's equivalent), keyed by `PluralRules` category.
- Text in an image is text no translator, screen reader or search engine reaches; set it as text over the image.
- Give translators context: a comment per key saying where the string appears and what fills each placeholder.
- A component receives its words from the caller rather than importing the whole dictionary; the pattern is in [candidates](candidates.md) ("A client component receives words").

**Cases**
- A sentence is built as `"Showing " + n + " of " + total + " results"` → one message with `{n}` and `{total}`; Japanese puts the total first.
- A banner's headline is part of the hero image → set the text in HTML over the image; the translated page otherwise shows English, and WCAG 1.4.5 Images of Text applies.
- A route builds its heading from a translation key while the story passes the design's own words → test the route, not the story (code-standard rule 56); the two can disagree for ever in a harness.
- Unused keys pile up in the dictionary → delete them or reference them; the lesson is in [candidates](candidates.md) ("Unused symbols are errors").

**Accessibility**
- 1.4.5 Images of Text (AA). 2.5.3 Label in Name: a translated visible label stays inside the translated accessible name, so `aria-label` strings are translated with the label they repeat.

**Check**
- *Script:* could flag string concatenation with a literal in templates and scripts, text nodes in templates that bypass the translation function, `content: "…"` with letters in sheets, and keys defined but never referenced.
- *Judgement:* Could a translator reorder every sentence on this page?

**Sources:** W3C Internationalization's [authoring techniques](https://www.w3.org/International/techniques/authoring-html) and the WCAG 2.2 criteria above. The toolkit follows them.

## Locale-aware sorting

**What good looks like**
- Any list sorted for a person to read (names, countries, facets) is sorted by `Intl.Collator` for the page's locale.
- Sorting for a machine (keys, ids, a stable diff) stays a plain code-point sort, and the two are not mixed.

**How**
- `list.sort(new Intl.Collator(lang).compare)`; options give `numeric: true` (so "item 2" precedes "item 10") and `sensitivity: "base"` for case- and accent-insensitive comparison. The same letters sort differently by locale: `ä` sorts after `a` in German and after `z` in Swedish ([MDN `Intl.Collator`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Collator)).
- Build one collator and reuse it; `localeCompare` in a sort callback builds one per comparison.
- Filtering by typed text uses the same collator's `sensitivity: "base"` so "e" finds "é".

**Cases**
- A country list sorts "Österreich" after "Zypern" → the collator; the default `sort()` compares UTF-16 code units.
- File names "v2" and "v10" sort as v10, v2 → `numeric: true`.
- A sorted list is also written to a file a test diffs → keep the machine sort there; a locale-dependent order makes a check depend on the machine (code-standard rule 35).

**Accessibility**
- No WCAG criterion names sorting; an order a reader can predict is design-standard *consistent, not uniform*.

**Check**
- *Script:* could flag `.sort()` with no comparator, or with `a < b`, on arrays of display strings.
- *Judgement:* Is this list sorted for a reader or for a machine?

**Sources:** MDN as linked.

## Font coverage

**What good looks like**
- Every script the product ships has a font that covers it, named in the stack, so no reader sees boxes or a jarring fallback.
- Web fonts load only the ranges a page needs.

**How**
- A family token lists fallbacks per script after the brand face: the brand Latin face, then a system face for Arabic, Hebrew, Devanagari or CJK, then the generic family (code-standard rule 54 says how a family is written).
- Split web fonts by script so a page downloads only the subsets its characters use; subsetting, `unicode-range` and loading are [performance: fonts](performance.md#fonts).
- `lang` chooses the right glyph variants for Han characters shared by Chinese and Japanese; it is a font concern as much as a reading one ([W3C, *Why use the language attribute?*](https://www.w3.org/International/questions/qa-lang-why)).
- Line height and vertical metrics differ by script; a fixed line height in px that suits Latin clips Thai or Devanagari stacked marks. Unitless line heights from tokens avoid it.

**Cases**
- The brand font has Latin only and the page ships in Arabic → name a system Arabic face in the stack and check the weights map; synthetic bold on a fallback is a visible failure.
- Vietnamese diacritics collide with the line above → raise the unitless line height for that locale, from a token.

**Accessibility**
- 1.4.12 Text Spacing: a line height that clips stacked marks fails the same readers a cramped one does.

**Check**
- *Script:* could render each locale and compare the font used for each text run against the family token (the browser's devtools protocol reports platform fonts per node).
- *Judgement:* Which scripts ship, and which face draws each one?

**Sources:** MDN and W3C as linked.
