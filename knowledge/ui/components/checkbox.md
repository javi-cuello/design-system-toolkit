# Checkbox

A checkbox picks any number of options from a set, none included, or turns one setting on that is saved with its form. This page owns the checkbox as a component, in design, in Figma and in code: the single box, the group in its `fieldset`, the indeterminate parent, "None of these", and its states. What spans the selection controls stays in [`../patterns/selection.md`](../patterns/selection.md): choosing the control, select all and clear all, multi-select and the dual listbox. Related: [radio](radio.md), [switch](switch.md), [chip](chip.md), [tables: selection and bulk actions](../patterns/tables.md#selection-and-bulk-actions).

## Overview

**Use when / don't use**
- [strong] A checkbox for any number of choices, or one setting, saved with a form; one choice of several is a radio and an instant setting a switch. The rule and its cases are [checkbox](#checkbox); the count that decides between checkboxes and a multi-select is [selection: choosing the control](../patterns/selection.md#choosing-the-control).
- [moderate] Two components and a container: the bare box (`Checkbox`), the box with its label, description and message (`Checkbox field`), and the group around fields. The bare box is placed alone where something else labels it, such as a table's row-selection column; the field is what forms use. Code splits the same way: SDS's `CheckboxField` renders its bare `Checkbox` with `Label`, `Description` and `FieldError` ([SDS Checkbox.tsx](https://github.com/figma/sds/blob/main/src/ui/primitives/Checkbox/Checkbox.tsx)), Primer's `Checkbox` has no label and takes one from `FormControl` ([Primer Checkbox source](https://github.com/primer/react/blob/main/packages/react/src/Checkbox/Checkbox.tsx)), Carbon, Atlassian and React Aria ship only the labelled form, so a library on them draws the bare box as the field's part.

**Anatomy**
- [moderate] The box holds its mark (a tick, or a dash when indeterminate); the field adds a label after it, an optional description under the label and, when it stands alone and fails, an error message under that. SDS names them `Label` and `Description` ([SDS CheckboxField.figma.ts](https://github.com/figma/sds/blob/main/src/figma/primitives/checkbox/CheckboxField.figma.ts)); Carbon `labelText` and `helperText` ([Carbon Checkbox source](https://github.com/carbon-design-system/carbon/blob/main/packages/react/src/components/Checkbox/Checkbox.tsx)).
- [strong] The group: a legend that asks the question, an optional hint, the options stacked, and an error message under the legend when the group fails validation ([forms: error messages and the error summary](../patterns/forms.md#error-messages-and-the-error-summary)).
- [required] The label is part of the target: a click on it toggles the box, as a `label` bound to its input does in HTML, so under WCAG 2.5.8 the box and its label together are the target; figma-standard rule 26 departs: it asks the bare box set for 24 by 24 on its own.
- [required] Focus shows a visible ring around the box (WCAG 2.4.7; figma-standard rule 39).

## Checkbox

**Use when / don't use**
- [strong] Use for any number of choices from a list, including none, in a form saved with a button.
- [moderate] Use a single checkbox for one setting saved with the form, or an agreement ("I agree to the terms").
- [strong] Don't use when only one choice may hold; that is radios ([GOV.UK checkboxes](https://design-system.service.gov.uk/components/checkboxes/)).
- [strong] Don't use as an action that happens on click ([NN/g, guideline 12](https://www.nngroup.com/articles/checkboxes-vs-radio-buttons/)); that is a switch or a button.

**How**
- [moderate] **Label to the right** of the box, and the label is part of the target: clicking the text toggles the box ([Carbon checkbox](https://carbondesignsystem.com/components/checkbox/usage/); [NN/g guideline 11](https://www.nngroup.com/articles/checkboxes-vs-radio-buttons/)).
- [strong] **Group** related boxes in a `fieldset` whose `legend` asks the question ("How would you like to be contacted?"). On a one-question page the legend is the page heading ([GOV.UK](https://design-system.service.gov.uk/components/checkboxes/)). Add the hint "Select all that apply" only when people are likely to pick one by habit.
- [moderate] **Stack vertically**, one per line ([NN/g guideline 6](https://www.nngroup.com/articles/checkboxes-vs-radio-buttons/); [Carbon](https://carbondesignsystem.com/components/checkbox/usage/): "When possible, arrange the checkbox and radio button groups vertically").
- [weak] **Wording** positive and active: "Send me updates", never "Don't send me updates" ([NN/g guideline 7](https://www.nngroup.com/articles/checkboxes-vs-radio-buttons/)).
- [weak] **Order** alphabetical by default, or most to least common where research shows a few answers dominate ([GOV.UK](https://design-system.service.gov.uk/components/checkboxes/)).
- [weak] **"None of these"** where none is a valid answer: last, after an "or" divider, and exclusive (checking it clears the others) ([GOV.UK](https://design-system.service.gov.uk/components/checkboxes/)).
- [moderate] **Indeterminate and select all.** A parent box over a sublist shows checked when all children are, empty when none are, and indeterminate when some are; checking the parent checks every child, unchecking clears them ([Carbon](https://carbondesignsystem.com/components/checkbox/usage/)). Indeterminate is a display state only: clicking an indeterminate parent checks all. Leave out the parent in a filter where "all" and "none" mean the same ([Carbon dropdown](https://carbondesignsystem.com/components/dropdown/usage/)).
- [weak] **States:** unchecked, checked, indeterminate, each with hover, focus, disabled and error.

**Cases**
- A form shows six interests as checkboxes in two columns → one column; two columns break the scan and the reader misses the second ([NN/g guideline 6](https://www.nngroup.com/articles/checkboxes-vs-radio-buttons/)).
- A table has a header checkbox to select rows and 3 of 20 are ticked → the header shows indeterminate; clicking it selects all 20, and the action bar says how many are selected.
- "Do not share my data" ticked by default → reword to "Share my data with partners", unticked; a negative label makes the person reason through a double negative.
- A checkbox labelled "Dark mode" applies the theme on click inside a settings page with no Save → a switch; a checkbox that acts at once breaks its promise.
- A list of dietary needs has no way to say "none" → add "None of these" last, behind a divider, exclusive; otherwise a person with no needs cannot answer a required question.

**Accessibility**
- [required] 1.3.1 Info and Relationships: the group's question is the `legend`. 3.3.2 Labels or Instructions: each box has its own label. 4.1.2 Name, Role, Value: the indeterminate state is exposed as mixed ([W3C APG checkbox](https://www.w3.org/WAI/ARIA/apg/patterns/checkbox/): `aria-checked="mixed"`; a native box sets its `indeterminate` property). 2.1.1 Keyboard: Space toggles. 2.5.8 Target Size: the label extends the target.
- [required] Implementation: code-standard rule 8 (the native `input type="checkbox"` inside the wrapper), code-standard rule 9 and code-standard rule 62 (disabled is the control's own), code-standard rule 15 (a hint is a description), code-standard rule 16 (native controls follow the theme). In a Figma component: figma-standard rule 26, figma-standard rule 31 (checked, indeterminate, hover, focus and disabled each draw differently), figma-standard rule 32.

**Build**
- [required] A native `<input type="checkbox">` inside the wrapper with its `label` after it, the group in a `fieldset` with a `legend` (code-standard rule 8; [HTML semantics: *Forms markup*](../../code/html-semantics.md#forms-markup)).
- [required] States are pseudo-classes: `:checked`, `:indeterminate`, `:focus-visible`, `:user-invalid`, and `:disabled` dimmed on the host through `:has(> :disabled)` (code-standard rule 9, code-standard rule 62).
- [required] A custom look draws on the input itself (`appearance: none`) so it keeps focus and its form value; never a hidden input behind a drawn `span`. Native boxes follow the theme (code-standard rule 16).
- [required] Indeterminate is the `indeterminate` property, set by the script; the parent and its children change in one handler ([accessibility: selection controls past the native set](../../code/accessibility.md#selection-controls-past-the-native-set)).
- [weak] "None of these" clears the others in a `change` handler; without script the server rejects the combination with an error.

**Check**
- *Script:* could check that every checkbox has a programmatic label, that a group of two or more sits in a `fieldset` with a `legend` or a labelled `role="group"`, that clicking a parent sets every child, and that no checkbox `change` causes navigation or a request without a submit.
- *Judgement:* Is the wording positive, and does a valid "none" answer exist?

**Sources:** GOV.UK, Carbon and NN/g as linked; they agree on every point used here.

## In Figma

**Layers**
- [required] Auto layout throughout. `Checkbox` is the box alone. `Checkbox field` holds a `Checkbox` instance, then the text column with `Label`, `Description` and `Error message`; the label wraps and the field grows with it (figma-standard rule 33). `Checkbox group` stacks `Legend` and `Description` above its `Options slot`, and `Error message` on the side the project takes ([where the error goes](#in-figma)).
- [required] Each layer is named for its role, the same in every variant: in `Checkbox`, `Box` and its mark `Icon`; in `Checkbox field`, the nested `Checkbox`, `Label`, `Description` and `Error message`; in `Checkbox group`, `Legend`, `Description`, `Error message` and `Options slot` (figma-standard rule 10). A text layer bound to a property takes the property's name.
- [required] The box leads and the text trails in auto-layout order, never by fixed position, so a right-to-left page mirrors it, where the project mirrors (figma-standard rule 50).
- [moderate] The box aligns to the label's first line, not the centre of a wrapped label, so a two-line label does not float its box ([GOV.UK checkboxes _mixin.scss](https://github.com/alphagov/govuk-frontend/blob/main/packages/govuk-frontend/src/govuk/components/checkboxes/_mixin.scss), [Carbon _checkbox.scss](https://github.com/carbon-design-system/carbon/blob/main/packages/styles/scss/components/checkbox/_checkbox.scss)).

**Properties**
- [required] `Checkbox field` has `Label` as a text property, `Show description` directly above `Description`, and `Show error message` directly above `Error message`, named for SDS's `errorMessage` prop (figma-standard rules 5, 21 and 37). The message is its own boolean, not `Validation`, because a field in a failed group shows no message of its own. SDS names the description boolean `Has Description` ([SDS CheckboxField.figma.ts](https://github.com/figma/sds/blob/main/src/figma/primitives/checkbox/CheckboxField.figma.ts)); figma-standard rule 21 keeps `Has` for content the component holds and `Show` for a boolean that reveals a layer.
- [required] `Checkbox group` holds `Legend`, `Show description` above `Description`, and a `Validation` axis (`None`, `Error`) whose `Error` variant adds `Error message`, over the code's `invalid` ([Carbon CheckboxGroup source](https://github.com/carbon-design-system/carbon/blob/main/packages/react/src/components/CheckboxGroup/CheckboxGroup.tsx)) (figma-standard rules 5, 30 and 57); a group has no failed parent to defer to, so its message needs no boolean of its own. Its boxes in a slot named for what it hosts (`Options slot`), never nested checkbox instances whose labels are text overrides, which a variant switch inside the parent drops (figma-standard rules 21 and 38).

**Variants and states**
- [contested] **One axis or two booleans.** Kits differ. SDS draws one `Value Type` axis and Carbon one `Selection` axis, each read by its Code Connect into two code booleans ([SDS CheckboxField.figma.ts](https://github.com/figma/sds/blob/main/src/figma/primitives/checkbox/CheckboxField.figma.ts), [Carbon Checkbox.figma.ts](https://github.com/carbon-design-system/carbon/blob/main/packages/react/code-connect/Checkbox/Checkbox.figma.ts)); Primer's kit draws `checked?` and `indeterminate?`, as its code has them ([Primer Checkbox.figma.tsx](https://github.com/primer/react/blob/main/packages/react/src/Checkbox/Checkbox.figma.tsx)). In code, `checked` and `indeterminate` are two booleans in the native input, Primer, React Aria (`isSelected`, `isIndeterminate`; [React Aria Checkbox](https://github.com/adobe/react-spectrum/blob/main/packages/react-aria-components/src/Checkbox.tsx)), Atlassian (`isChecked`, `isIndeterminate`; [Atlassian checkbox props](https://atlassian.design/components/checkbox/code)) and Material Web ([Material Web checkbox.ts](https://github.com/material-components/material-web/blob/main/checkbox/internal/checkbox.ts)); Fluent folds them into one prop, `checked: 'mixed' | boolean` ([Fluent Checkbox.types.ts](https://github.com/microsoft/fluentui/blob/master/packages/react-components/react-checkbox/library/src/components/Checkbox/Checkbox.types.ts)), and Radix into `checked: boolean | 'indeterminate'` ([Radix checkbox source](https://github.com/radix-ui/primitives/blob/main/packages/react/checkbox/src/checkbox.tsx)); no kit read here draws a three-value prop's axis. figma-standard rule 56 departs from SDS and Carbon: it takes the shape of the project's code, `Checked` and `Indeterminate` as `False`/`True` properties over two booleans, as Primer's kit does.
- [required] With two booleans, `Checked=True, Indeterminate=True` is drawn, and shows the dash: code reaches it, since "an input element's indeterminateness is independent of its checkedness" ([HTML](https://html.spec.whatwg.org/multipage/input.html#concept-input-indeterminate)); Atlassian's `isIndeterminate` "only affects the style and does not modify the isChecked property" ([Atlassian checkbox props](https://atlassian.design/components/checkbox/code)), and Material Web draws the tick only for `checked && !indeterminate` ([Material Web checkbox.ts](https://github.com/material-components/material-web/blob/main/checkbox/internal/checkbox.ts)). It is not a selection that contradicts itself, so figma-standard rule 2 keeps it, and figma-standard rule 51 draws what code renders.
- [required] The box and the field have the axes `Checked → Indeterminate → Validation → Disabled → State` (figma-standard rule 56 for `Checked` and `Indeterminate`; one `Checked` axis where the code has one prop). `Validation` lists `None` then `Error`; `Disabled` pairs only with Rest and sits right after it, and pairs with Focus too where the code keeps it focusable; `State` runs `Rest → Focus → Hover → Press` (figma-standard rules 1 to 4 and 57). The states themselves are in [checkbox: *How*](#checkbox).
- [moderate] Disabled never combines with Error, so the bare box is 36 variants: 4 `Checked` and `Indeterminate` pairs × (4 states without error, 4 with error, 1 disabled); 27 on a three-value axis. Carbon drops `invalid` whenever `disabled` is set (`invalid: !readOnly && !disabled && invalid`, [Carbon useNormalizedInputProps](https://github.com/carbon-design-system/carbon/blob/main/packages/react/src/internal/useNormalizedInputProps.tsx)). Material 3 defines error tokens for rest, hover, focus and pressed, selected and unselected, and none for disabled ([Material Web checkbox tokens](https://github.com/material-components/material-web/blob/main/tokens/_md-comp-checkbox.scss)). A disabled field cannot be corrected, so an error on it is a message with no remedy (beyond figma-standard rule 2, which pairs Disabled with Rest, and with Focus only where the control stays focusable).
- [strong] **Where the error goes.** In a group, the error belongs to the group: one message under the legend and its hint, above the options (the side is the contested item below), and the fields inside take `Show error message` off; whether their boxes also take `Validation=Error` follows the contested item below. GOV.UK renders the checkboxes' `errorMessage` after the hint and before the items ([GOV.UK checkboxes template](https://github.com/alphagov/govuk-frontend/blob/main/packages/govuk-frontend/src/govuk/components/checkboxes/template.njk)); SDS's `CheckboxGroup` puts `FieldError` after `Label` and `Description` and before its children ([SDS Checkbox.tsx](https://github.com/figma/sds/blob/main/src/ui/primitives/Checkbox/Checkbox.tsx)); Carbon's `CheckboxGroup` takes `invalid` and `invalidText` for the set. A checkbox standing alone ("I agree to the terms") is its own question, so `Checkbox field` turns `Show error message` on and shows it under the label, as SDS's `CheckboxField` does. The group draws its message through its own `Show error message` and `Error message`.
- [contested] **Above or below the options.** GOV.UK and SDS put the group's message above the options; Carbon's `CheckboxGroup` renders it after them ([Carbon CheckboxGroup source](https://github.com/carbon-design-system/carbon/blob/main/packages/react/src/components/CheckboxGroup/CheckboxGroup.tsx)), Primer shows it after them while reading it out inside the `legend` ([Primer CheckboxOrRadioGroup source](https://github.com/primer/react/blob/main/packages/react/src/internal/components/CheckboxOrRadioGroup/CheckboxOrRadioGroup.tsx)), and MUI's group demo puts `FormHelperText` after its `FormGroup` ([MUI checkbox group demo](https://github.com/mui/material-ui/blob/master/docs/data/material/components/checkboxes/demos/group/CheckboxesGroup.tsx)). GOV.UK puts every field's message above its control; a project's group message sits on the side its field messages take ([forms: *Error messages and the error summary*](../patterns/forms.md#error-messages-and-the-error-summary)).
- [contested] **Whether the boxes turn red too.** Material 3, Carbon and Atlassian style the box in error (Material's `selected-error-*` and `unselected-error-*` tokens, Carbon's `invalid`, Atlassian's `isInvalid` on [Checkbox types](https://unpkg.com/@atlaskit/checkbox/dist/types/types.d.ts)); Primer gives a single checkbox no error style and uses `validationStatus` "only to inform ARIA attributes" ([Primer Checkbox source](https://github.com/primer/react/blob/main/packages/react/src/Checkbox/Checkbox.tsx)), and MUI's `Checkbox` takes no `error` prop while `FormControlLabel` turns the label red from its `FormControl` ([MUI Checkbox types](https://github.com/mui/material-ui/blob/master/packages/mui-material/src/Checkbox/Checkbox.d.ts), [MUI FormControlLabel source](https://github.com/mui/material-ui/blob/master/packages/mui-material/src/FormControlLabel/FormControlLabel.js)).
- [required] The field owns its box's state: it sets the nested `Checkbox`'s variant from its own axes and does not expose the instance, so a field in error cannot hold a box at rest. Hovering or pressing the label acts on the box, so the field's `State` drives the box's (figma-standard rule 7).
- [moderate] `Checked`, `Indeterminate` and `Validation` sit beside `State`, not on it, because each combines with every pointer state: a focused box in error is a frame the developer otherwise builds unseen, and code sets both as props while the browser sets the pointer states ([research: *States on the axis*](../../../research/components-and-naming/what-the-state-axis-models.md#states-on-the-axis)). The [radio](radio.md#in-figma) and [switch](switch.md#in-figma) link here.

**Tokens**
- [required] Every fill, stroke, radius, gap and padding binds a semantic variable, never a primitive; the label takes a text-role token (figma-standard rules 24, 28 and 29).
- [required] A state variant binds its own state's tokens (figma-standard rule 48); the mark keeps one token across pointer states where it never changes.
- [required] The unchecked box's border meets 3:1 against its surface, and the mark 3:1 against the checked fill (WCAG 1.4.11), in every mode (beyond figma-standard rule 32, which covers text).
- [required] Component tokens, where the project has them, are `Component/Checkbox/<Element>/<property>[-<variant>][-<state>]` aliasing semantic ones (figma-standard rule 49).

**Check**
- *Script*: figma-components-audit runs the rules cited above on the set; the snapshot's contract lists `Checked`, `Indeterminate`, `Validation` and `Disabled`, so an axis with no code counterpart shows in the parity report.
- *Judgement*: does each checked property carry its code prop's name and values, so Code Connect maps it straight across, and can a designer draw a select-all parent in each of its states?

**Sources.** HTML, Primer, Atlassian, Material Web, Fluent and Radix for the checked state's shape; Figma's Simple Design System for the property names, Carbon for the group's legend; SDS, Carbon, Material 3, Primer and GOV.UK for the control and field split and where the error goes; the toolkit's research article *What the State axis models* (research folder, November 2026) for what sits beside `State`. ## Alignment with code

**Structure**
- [strong] Code splits the checkbox three ways, and the three sets in [In Figma](#in-figma) mirror it: a bare box, a field that adds the label, description and message, and a group that adds the legend and the group's message. SDS ships `Checkbox`, `CheckboxField` and `CheckboxGroup` ([SDS Checkbox.tsx](https://github.com/figma/sds/blob/main/src/ui/primitives/Checkbox/Checkbox.tsx)); React Aria `CheckboxButton`, `CheckboxField` and `CheckboxGroup`, its single `Checkbox` deprecated for the pair ([React Aria Checkbox.tsx](https://github.com/adobe/react-spectrum/blob/main/packages/react-aria-components/src/Checkbox.tsx)); Primer a bare `Checkbox` placed in `FormControl` with `FormControl.Label` and `FormControl.Caption`, and `CheckboxGroup` ([Primer Checkbox.figma.tsx](https://github.com/primer/react/blob/main/packages/react/src/Checkbox/Checkbox.figma.tsx), [Primer CheckboxGroup.figma.tsx](https://github.com/primer/react/blob/main/packages/react/src/CheckboxGroup/CheckboxGroup.figma.tsx)); MUI `Checkbox` inside `FormControlLabel`, grouped by `FormControl component="fieldset"` with `FormLabel` and `FormGroup` ([MUI checkbox group demo](https://github.com/mui/material-ui/blob/master/docs/data/material/components/checkboxes/demos/group/CheckboxesGroup.tsx)).
- [moderate] Carbon and Radix sit at the two ends and still map onto the three sets. Carbon's `Checkbox` is always the field (`labelText`, `helperText`, `invalidText`), a bare box only through `hideLabel`, beside a `CheckboxGroup` with `legendText` ([Carbon Checkbox.figma.ts](https://github.com/carbon-design-system/carbon/blob/main/packages/react/code-connect/Checkbox/Checkbox.figma.ts), [Carbon CheckboxGroup.figma.ts](https://github.com/carbon-design-system/carbon/blob/main/packages/react/code-connect/Checkbox/CheckboxGroup.figma.ts)); Radix ships only the box, `Checkbox.Root` and `Checkbox.Indicator`, and leaves the label and message to its separate Form primitive ([Radix checkbox exports](https://github.com/radix-ui/primitives/blob/main/packages/react/checkbox/src/index.ts), [Radix form exports](https://github.com/radix-ui/primitives/blob/main/packages/react/form/src/index.ts)).
- [contested] **A message on a lone checkbox.** SDS, React Aria and Carbon let a checkbox outside a group carry its own error (`FieldError` in each `CheckboxField`, Carbon's `invalidText`); Primer refuses, its `FormControl` warning that "Validation messages are not rendered for an individual checkbox or radio" ([Primer FormControl source](https://github.com/primer/react/blob/main/packages/react/src/FormControl/FormControl.tsx)). `Checkbox field`'s `Show error message` serves a project on the three's side; a project on Primer gives a lone checkbox a one-item `CheckboxGroup` for its message, and records that.
- [strong] Inside a group the field's own message goes quiet: React Aria's `CheckboxField` drops its error when it sits in a `CheckboxGroup` ("validation is handled at the group level instead of repeated on each checkbox", [React Aria Checkbox.tsx](https://github.com/adobe/react-spectrum/blob/main/packages/react-aria-components/src/Checkbox.tsx)), and Primer's `CheckboxGroup.Validation` and Carbon's group `invalidText` carry one message for the set. That is the field with `Show error message` off in [In Figma](#in-figma).

**Mapping**
- [required] Each Figma axis maps to one attribute, property or pseudo-class, recorded once (code-standard rules 9 and 10; [figma-handoff: *Variants to attributes*](../../code/figma-handoff.md#variants-to-attributes)):

  | Figma | Code |
  |---|---|
  | `Checked=False` | no `checked` |
  | `Checked=True` | `checked`, styled from `:checked` |
  | `Indeterminate=True` | the `indeterminate` property set by script, styled from `:indeterminate` |
  | `Checked=Mixed` or `Checked=Indeterminate` (one axis) | the library's three-value prop (`checked="mixed"`, `checked="indeterminate"`) |
  | `Validation=Error` | `aria-invalid="true"`; styled from `:user-invalid` or the attribute |
  | `Show error message`, `Error message` | the field's `errorMessage`, or the group's, tied with `aria-describedby` to the field or to the `fieldset` |
  | `Checkbox` alone | the bare box, labelled by what places it (`aria-label`, or a row header with `aria-labelledby`) |
  | `Disabled=True` | `disabled` on the input |
  | `State=Hover`, `Press`, `Focus` | `:hover`, `:active`, `:focus-visible`, set by the browser |
  | `Label`, `Description` | the `label`; the description tied with `aria-describedby` (code-standard rule 15) |

**States**
- [required] The browser sets `:checked` on a click or Space, the pointer and focus states in the mapping, and `:user-invalid` on a `required` box left unchecked once the person has interacted or submitted ([HTML: `:user-invalid`](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-user-invalid); Chrome 119, Firefox 88, Safari 16.5 by [MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Selectors/:user-invalid)). `:indeterminate` comes only from script, and a click clears it ([HTML: indeterminateness](https://html.spec.whatwg.org/multipage/input.html#concept-input-indeterminate)).
- [required] A prop sets the rest: `disabled`, `indeterminate`, and `aria-invalid` for any error `required` cannot express. A checked `required` box satisfies its constraint, so `Checked=True` with `Validation=Error` is reached only through `aria-invalid` (a server's verdict), and the stylesheet styles error from the attribute as well as `:user-invalid`.
- [required] Code cannot reach Disabled with Error, which is why the sets draw none: a disabled control is barred from constraint validation, so `:user-invalid` never matches it ([HTML: the disabled attribute](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#attr-fe-disabled)), and Carbon drops `invalid` under `disabled` as [In Figma](#in-figma) cites.
- [required] Code reaches a box both checked and indeterminate, the `Checked=True, Indeterminate=True` frame: "an input element's indeterminateness is independent of its checkedness" ([HTML](https://html.spec.whatwg.org/multipage/input.html#concept-input-indeterminate)), so `:checked` and `:indeterminate` both match. Write `:indeterminate` after `:checked`, so the dash wins as that frame shows.
- [moderate] Code reaches every pointer state on every `Checked` and `Indeterminate` value and with error, and a person tabbing back to fix a box meets focus with error; the sets draw them because `Checked`, `Indeterminate` and `Validation` sit beside `State` ([In Figma](#in-figma)).
- [moderate] React Aria sets every state as a data attribute from script (`data-hovered`, `data-pressed`, `data-focus-visible`, `data-indeterminate`, `data-invalid`; [React Aria Checkbox.tsx](https://github.com/adobe/react-spectrum/blob/main/packages/react-aria-components/src/Checkbox.tsx)) and Radix sets `data-state="checked"`, `"unchecked"` or `"indeterminate"` ([Radix checkbox source](https://github.com/radix-ui/primitives/blob/main/packages/react/checkbox/src/checkbox.tsx)), so on those libraries the stylesheet matches their attributes, not the pseudo-classes in the mapping.

**Differences**
- [contested] Kits differ on the checked state ([In Figma](#in-figma)). SDS's `Value Type` and Carbon's `Selection` read one Figma value into two code props, and their sets draw no box both checked and indeterminate, which code reaches ([Carbon Checkbox.figma.ts](https://github.com/carbon-design-system/carbon/blob/main/packages/react/code-connect/Checkbox/Checkbox.figma.ts), [SDS CheckboxField.figma.ts](https://github.com/figma/sds/blob/main/src/figma/primitives/checkbox/CheckboxField.figma.ts)); Primer's kit draws `checked?` and `indeterminate?` as its code has them ([Primer Checkbox.figma.tsx](https://github.com/primer/react/blob/main/packages/react/src/Checkbox/Checkbox.figma.tsx)). figma-standard rule 56 departs from the first two.
- [required] `Disabled` is an axis of its own where the SDS, Carbon and Primer kits fold it into `State` (`State=Disabled` read as `isDisabled` or `disabled` in each Code Connect file above): code sets it as a prop and the browser sets the pointer states (figma-standard rule 1).
- [required] Carbon's kit carries `Read-only` and `Warning` as `State` values, mapped to `readOnly` and `warn` ([Carbon Checkbox.figma.ts](https://github.com/carbon-design-system/carbon/blob/main/packages/react/code-connect/Checkbox/Checkbox.figma.ts)), and React Aria has `isReadOnly` (source above); a set draws either only where the project's code renders it (figma-standard rule 51).
- [moderate] The text properties take SDS's prop names (`Label`, `Description`, `Error message`); Primer's are `Label`, `Caption` and `Validation`, Carbon's `labelText`, `helperText` and `invalidText`. The mapping row is where a project's names meet its kit's (figma-standard rule 21).

**Check**
- *Script*: the component contract lists the three sets' axes and properties beside the code's components and props; a set with no code component (a field on Radix) or a prop with no frame, and no line under *Differences*, is a finding (design-code-parity).
- *Judgement*: does each set name the code component it becomes, and does a box in a failed group show no message of its own in Figma and in code?

**Sources.** SDS, React Aria, Primer, MUI, Carbon, Radix, Atlassian, Material Web and Fluent source and Code Connect files as linked; the HTML standard for `:user-invalid`, indeterminateness and disabled controls; MDN for browser support.

## In code

**Element**
- [required] The native `input type="checkbox"` inside the wrapper, its `label` after it, the group a `fieldset` with a `legend`, as [checkbox: *Build*](#checkbox) sets out (code-standard rule 8). Radix renders a `button role="checkbox"` with `aria-checked="mixed"` and a hidden input for forms ([Radix checkbox source](https://github.com/radix-ui/primitives/blob/main/packages/react/checkbox/src/checkbox.tsx)); the native input needs neither.
- [required] Indeterminate has no HTML attribute: it is the `indeterminate` property, set by script and matched by `:indeterminate`, so server-rendered markup cannot carry it ([HTML: the checkbox state](https://html.spec.whatwg.org/multipage/input.html#checkbox-state-(type=checkbox))).

**Props**
- [strong] `checked` (or `defaultChecked`), `indeterminate`, `disabled`, `required`, a validation prop, the label and a description. Primer (`indeterminate`, `disabled`, `required`, `validationStatus`; [Primer Checkbox source](https://github.com/primer/react/blob/main/packages/react/src/Checkbox/Checkbox.tsx)), Carbon (`indeterminate`, `invalid`, `warn`, `labelText`, `helperText`; [Carbon Checkbox source](https://github.com/carbon-design-system/carbon/blob/main/packages/react/src/components/Checkbox/Checkbox.tsx)), MUI (`indeterminate`, `size`, `color`; [MUI Checkbox source](https://github.com/mui/material-ui/blob/master/packages/mui-material/src/Checkbox/Checkbox.js)) and React Aria (`isSelected`, `isIndeterminate`, `isInvalid`; [React Aria Checkbox](https://github.com/adobe/react-spectrum/blob/main/packages/react-aria-components/src/Checkbox.tsx)) share this shape.
- [strong] Indeterminate is a boolean beside `checked` in Primer, Carbon, MUI, React Aria, Atlassian and Material Web; Fluent (`checked: 'mixed' | boolean`) and Radix (`checked: boolean | 'indeterminate'`) fold it into one prop. figma-standard rule 56 has the Figma set take the project's code's shape ([In Figma](#in-figma)).

**Check**
- *Script*: the parity loop compares each variant's box, mark and ring with its frame (design-code-parity); the component contract flags a Figma axis with no prop.
- *Judgement*: does the indeterminate parent survive a server render, set by script after load?

**Sources.** Primer, Carbon, MUI, React Aria and Radix source as linked; the HTML standard for the indeterminate property; the toolkit's state-axis research for the mapping table in *Alignment with code*.
