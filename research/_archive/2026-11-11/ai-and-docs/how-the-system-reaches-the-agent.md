# How a design system reaches the agent

Rules, reference and a portable snapshot are three kinds of knowledge that fail in different ways, so they belong in three places; the reference is best served on demand, and the context file kept to the instructions the code cannot state.

Part 4 of 9 in *The agent-ready design system*. Previous: [Part 3, One record, many outputs](design-system-docs-as-one-record.md) Next: [Part 5, What keeps an agent on a design system](what-keeps-an-agent-on-track.md)

A design-system team with a well-described library (Part 2) and one record of it (Part 3) still has to get that record in front of an agent at the moment the agent needs it. This piece compares the routes: a context file, a server, a skill, a CLI, an `llms.txt`, a portable `DESIGN.md`. It covers what the two controlled studies of context files found, which systems ship which route, and what the one published head-to-head test says.

## 1. Where should rules, reference and snapshots live?

In three places, because they fail differently. **Rules** are short imperative constraints, written by a person and always in context, so every line costs on every turn. **Reference** is the bulk (component APIs, token values, usage), generated by a pipeline and fetched only when asked. A **snapshot** is one self-contained description of the visual identity, which travels anywhere and loads in full every time.

| Layer | What it holds | Where it lives | Loaded when | Written by |
|---|---|---|---|---|
| Rules | What never to do | `AGENTS.md`, `CLAUDE.md`, `SKILL.md` | Always, or on trigger | A person |
| Reference | Component APIs, token values, usage | An MCP server, a CLI, skills, schema files | On demand | A pipeline |
| Snapshot | The visual identity in one file | `DESIGN.md` | All at once | Generated, then tuned |

Rules rot when nobody prunes them, reference goes stale when the pipeline stops, and a snapshot is out of date the moment it is written. The common failure is one enormous file that tries to be all three, loads everything every turn, and buries the handful of instructions that change behaviour.

**What to do.** Keep the three apart, each written by whoever can keep it true: a person for the rules, a pipeline for the reference, a generator tuned by hand for the snapshot. **One file that tries to be all three costs on every turn and hides the few lines that matter.** The three-layer split is consensus among the vendors cited below; the table is this series' summary of it.

## 2. Do `AGENTS.md` files help, and what belongs in one?

Two controlled studies exist and they answer different questions: one found no general gain in task success at higher cost, the other found faster runs without measuring correctness. Both point at the same part worth keeping (instructions the code cannot state about itself) and the same part to delete (the repository overview).

`AGENTS.md` is the cross-tool convention for repository rules. It was released by OpenAI in August 2025 and donated to the Linux Foundation's Agentic AI Foundation on 9 December 2025, and it is read by Codex, Cursor, Copilot, Gemini CLI and others. The nearest file to the edited code wins.

- **Gloaguen et al.** (ETH Zurich and LogicStar.ai, arXiv:2602.11988, version 3 of 29 September 2026) ran four frontier models with no context file, a generated one and a developer-written one, on SWE-bench tasks and on issues from repositories that ship their own files. Context files "do not generally improve task success rates, while increasing inference cost by over 20% on average", across models, agents and both kinds of file. Inside that result, the instructions were well followed, while repository overviews, though popular and recommended by model providers, were not helpful. The latest version's conclusion adds the useful half: context files are useful for specifying non-standard coding practices, and any attempt to improve performance with them should be evaluated before it is deployed.
- **Lulla et al.** (ICSE JAWs 2026, arXiv:2601.20404) ran 124 real pull requests from 10 repositories twice with `gpt-5.2-codex`, with and without the repository's own `AGENTS.md`. Median runtime fell 28.64 percent (98.57 to 70.34 seconds) and median output tokens 16.58 percent (2,925 to 2,440). It measured efficiency, not correctness.

A file that makes an agent finish faster without making it finish correctly more often is consistent with both. Neither licenses "AGENTS.md is proven to help" or "proven not to".

Four traps follow from them.

- **The generated repository overview.** Usually the longest section, and the one found unhelpful.
- **The context file as documentation.** Anything discoverable from the code does not belong.
- **The auto-generated file.** The cheapest, and the setting with no success benefit.
- **The unbounded file.** Cost scales with length on every call.

For skills, Anthropic's guidance loads three levels: name and description at startup (about 100 tokens a skill), the body once triggered (under 500 lines), and bundled files only when referenced.

Even a well-written rule is advisory: the model may judge that it does not apply, and the step that must happen every time needs a hook ([Part 6, section 1](agent-workflow-enforcement.md#1-why-does-a-written-step-feel-optional)).

**What to do.** Write rules by hand as imperative constraints, delete the repository overview, and turn anything deterministic into a lint rule or a check: zero tokens, no compliance question. **The lines that earn their tokens are the instructions the code cannot state about itself.** That reading is shared by both studies; neither measured design-system work specifically.

## 3. Should the reference be served on demand or all at once?

On demand, for an established codebase. The one published head-to-head is decisive, the vendors who measured agree on direction, and the remaining choice (server or CLI) is about a team's tooling, not settled evidence.

Atlassian ran the same task, building a login screen, with four kinds of context:

| Context given to the agent | Guidance reached | Tokens | Time | Turns |
|---|---|---|---|---|
| None | about 5% | 4.20M | 6m 19s | 43 |
| Atlassian's MCP server | about 80% | 3.75M | 5m 01s | 35.1 |
| Atlassian's skill | about 80% | 4.43M | 5m 23s | 36 |
| Portable `DESIGN.md` | about 30% | 7.21M | 6m 46s | 45.3 |

Atlassian named three causes.

- **All at once against on demand.** The file loads in full every turn, while a server answers a narrow question narrowly.
- **Portability forces compression, and compression cuts the useful part.** To stay portable the file was squeezed to 80KB (about 19,800 tokens) against roughly 2.5MB the server can draw on, and "we had to remove much of the usage guidance from our 50+ components", along with foundation guidance and a number of design tokens.
- **A complete visual specification is a build recipe.** Agents re-created Atlassian's components rather than importing them.

Atlassian also had to ship a separate dark-mode file, because the format has no theming. It calls its own results not conclusive and publishes no run counts.

**The other measured claims.** Storybook reported, for the Reshaped library with its MCP docs against a baseline, 12.8 percent better code usage, 2.76 times faster and 27 percent fewer tokens. The figures appear only in an image caption on Storybook's blog, with no tasks, models or run counts, and the RFC behind the experiment (9 September 2025) judged the docs Claude generated for every export of the package, in about 26 minutes and for about $15, "not accurate, it's not consistent, and it's not exhaustive". Without the server, its agents generated their own components, typically with shadcn/ui and Tailwind.

Atlassian's later CLI post reports an 8 percent cut in session time (352 to 325 seconds) and tokens (218k to 201k) against its own MCP server, and CLI usage overtaking MCP usage, which is one team's data.

**What to do.** Serve generated reference on demand from whatever the team already runs (a docs site's JSON, a server over it, or a CLI) and keep the rules file short. **An all-at-once file cost more than no context at all in the only head-to-head, so the reference is fetched, never preloaded.** The direction is consensus among the vendors who measured; the size of the effect rests on one team's test with no published run counts.

## 4. Which design systems ship a server, skills or an `llms.txt`, and what do they serve?

Atlassian, Primer, Carbon and Spectrum ship design-system MCP servers; Polaris folds into Shopify's developer server; Salesforce ships skills only; Fluent and GOV.UK ship none. The roster below is as of 4 November 2026 (Primer's tool count as of 9 November).

- **Atlassian's `@atlaskit/ads-mcp`**, in Early Access, can run locally or from a hosted endpoint. Its tools are `ads_plan`, search tools for components, tokens and icons (`ads_search_components`, `ads_search_tokens`) and axe-based accessibility tools such as `ads_analyze_a11y`, and its content is regenerated from ADS's structured content.
- **Primer's `@primer/mcp`** has nineteen tools, among them `list_components`, `get_component`, `find_tokens` ("by intent or value") and `lint_css`. It serves component APIs, examples, usage and accessibility guidelines, and patterns: `list_patterns` and `get_pattern` tell the agent to prefer a scenario pattern (Create, Edit, Filter, View and others) when one fits. Its `PageLayout` is reachable only as a component.
- **Carbon** has a hosted server behind IBMid, serving "components, tokens, icons, guidance, and code"; its concepts page names the tools `code_audit`, `code_search`, `docs_search`, `get_charts` and `labs_search`.
- **Spectrum** ships `@react-spectrum/mcp`, agent skills and an `llms.txt`.
- **Polaris** folds its tooling into Shopify's `@shopify/dev-mcp`.
- **Salesforce** ships no server, only three agent skills that call the SLDS Linter.
- **Fluent and GOV.UK**: no official server was found.
- **Ant Design and shadcn/ui** ship servers too; what they serve for whole screens is in [Part 7, section 3](building-screens-with-an-agent.md#3-should-the-design-systems-mcp-server-serve-page-layouts).
- **`llms.txt`** is live at atlassian.design, carbondesignsystem.com and react-spectrum.adobe.com, and returns 404 at primer.style and the GOV.UK design system. shadcn/ui publishes one too.

Figma's own MCP server reads the design side: `get_design_context` returns code for a selection (React and Tailwind by default), `get_variable_defs` lists the variables a selection uses, and `search_design_system` searches connected libraries.

Atlassian's prototyping work, which collapsed its guidance into one file and moved the navigation into configuration, is told in [Part 7, section 2](building-screens-with-an-agent.md#2-rules-templates-or-example-screens-which-carries-screen-conventions).

**What the toolkit built.** The design-system toolkit took the on-demand route without a separate pipeline. Its docs site writes a JSON API beside its pages at build time, and `tools/system-mcp` (named `docs-mcp` until 4 November 2026) is a read-only MCP server over that API for one project at a time ([server README](https://github.com/javi-cuello/design-system-toolkit/blob/main/tools/system-mcp/README.md)).

Its tools are `overview`, `search`, `get_contract`, `get_component`, `get_tokens`, `get_changes`, `get_audit`, `get_screen_recipe`, `list_pages`, `read_page` and `validate`. The reference is whatever the site renders, so the server cannot say something the docs do not. It had no `llms.txt` and no Markdown page variants as of November 2026. Whether an agent actually calls a loaded server depends on its instructions, a finding told in [Part 5, section 3](what-keeps-an-agent-on-track.md#3-how-does-an-agent-get-more-without-reading-everything).

**What to do.** Add an `llms.txt` (an H1, a blockquote summary, H2 sections of links, an `Optional` section) and Markdown page variants when a docs site exists: an afternoon's work for agents that do not speak MCP. **A server is worth building only over a record that is already generated, so the server can never say something the docs do not.** That the large systems ship servers is a fact of November 2026; that a server should sit over the docs' own data is this series' judgment.

## 5. When is a portable `DESIGN.md` the right choice?

For green-field work, a small team or a hand-off outside the team's infrastructure. Atlassian's three objections are brownfield objections; where there is no coded library to import, a portable identity file with nothing to run is the simplest working route.

`DESIGN.md` is not trying to be a server. It is a portable, version-controllable description of an identity that works in any tool with nothing to run. Google Labs ships a CLI that lints, diffs and exports it (a Tailwind v4 `@theme` block since 0.2.0). The format is at 0.4.0 (27 July 2026), still pre-1.0, with no theming support in any release.

**The middle position.** A CLI that answers narrow questions gets the on-demand property of a server and the nothing-to-run property of a file. Meta's Astryx (open-sourced in beta in June 2026, React and StyleX, around 13,000 internal apps) states the design: its API, docs and CLI are designed together, so that a person and an AI assistant build the same way from the same reference. Its README names a CLI for "component docs, templates, scaffolding, themes, and codemods"; it names no MCP server and no JSON manifest.

**What to do.** For green-field work, ship the snapshot with an explicit instruction to prefer existing components, and one file per theme until the format supports theming. **Choose the portable file when there is nothing to import yet, and the on-demand route once there is.** The split by brownfield and green-field is this series' reading of Atlassian's three objections.

## 6. Cheat sheet

| For an agent to | Put it here | Not here |
|---|---|---|
| Follow the few rules the code cannot state | A short, hand-written rules file | A generated overview |
| Understand the repository layout | Nowhere; delete the overview | The top of `AGENTS.md` |
| Look up a component's API or a token | A server, CLI or skill over generated reference | A file loaded on every turn |
| Be blocked from a mistake | A lint rule or a check it runs (Parts 5 and 6) | Any context file |
| Work outside the team's infrastructure | A portable snapshot, or a CLI | A server with no fallback |
| Reach a docs site without MCP | An `llms.txt` and Markdown page variants | A 2MB dump |

---

## 7. The short version

Keep rules, reference and snapshots apart. Rules are short and hand-written, and load every turn, so every line has to earn its cost. Reference is the bulk, generated, and fetched only when asked. A snapshot is one portable file for tools that can reach nothing else.

Of the two `AGENTS.md` studies, one found no general gain in task success at over 20 percent more cost and the other found faster runs without checking correctness. Both point at the same thing to keep, instructions the code cannot state about itself, and the same thing to delete, the repository overview.

Serve the reference on demand: in Atlassian's test an all-at-once file cost more than no context at all, and a server or skill reached about 80 percent of the guidance. Atlassian, Primer, Carbon and Spectrum ship servers; an `llms.txt` is an afternoon's work for agents that do not speak MCP. A portable `DESIGN.md` still has a place for green-field work, with one file per theme until the format supports theming.
