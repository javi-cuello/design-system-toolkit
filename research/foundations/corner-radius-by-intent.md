# Corner radius by intent

*How to build a radius model that says what a corner is for as well as how round it is, from the scale to code, Figma and a migration.*

A product team lines up its form controls for a review. The button is 6px round, the text input 4px, the select 8px, and the date picker someone built last spring 5px. A card at 16px holds a cover image that is also 16px, and its corners look swollen. On phones, the bottom sheet keeps its rounded bottom corners pressed against the edge of the screen. Then the brand team asks for everything to be "a little softer" next quarter.

None of those values is wrong on its own. What is missing is a model: a short scale, a few roles, and rules for corners inside corners, at a screen's edge and in a softer theme.

# The model

## The radius scale

Keep one short scale of six to ten steps, from none to full, and name the steps by number, as a spacing scale is named, so a new one can be added without renaming the rest.

The opening's four controls have four radii because each was chosen by eye on the day it was built. A scale ends that: it is the list of values a corner may take.

Shipping scales are short: Primer has four steps plus a default, Atlassian eight, Polaris and Material ten, Fluent eleven. Spacing scales run to fifteen or more, but a reader can tell 4px from 6px on a button and rarely 24px from 28px on a dialog.

Naming is settled in [spacing tokens by intent](spacing-tokens-by-intent.md#the-primitive-scale): multiplier or value names, no t-shirt words in the primitive layer. Radius scales lean on t-shirt words more, so here are the schemes on one scale.

Under each corner are the names systems give it: t-shirt words (Atlassian `radius.medium`, Material `corner.medium`), value names (Carbon v12 `border-radius-04`, 4px) and indexes (Radix `--radius-3`). Polaris uses its spacing multipliers: `border-radius-100` is 4px.

The scheme matters when a step arrives later. Material had to coin `large-increased` (20dp) and `extra-large-increased` (32dp) in January 2025 to wedge steps between its t-shirt names. Spectrum 2 reused the index `corner-radius-200` for 5px when it had meant 8px in Spectrum 1, so the same name now draws a different corner. Polaris moved from words to an index to multipliers, each time with a codemod, because an index could not say 30px.

**Keep six to ten steps from `none` to `full`, named by value (`radius-4`) or by multiplier with the base stated (`radius-100`), as the spacing scale is, so a step added later slots in without renaming its neighbours.** T-shirt words belong one layer up, on [roles](#roles-on-top). *Weight: moderate.* Material's wedged names and the indexes Polaris renamed and Spectrum reused are the costs of the other choices.

## Roles on top

Put a small role layer over the scale (detail, control, container, overlay, full) so that every button, input and select takes one token, and a change to controls is one edit.

A scale alone does not stop four controls taking four radii, since two steps are both valid for an input. A token that names the job does: `radius.control`, used by everything a person presses or types into.

Atlassian does this in its token descriptions: `radius.medium` is for buttons, inputs and selects, `radius.large` for cards and menus, `radius.full` for avatars, so its t-shirt names work as roles. Here is that mapping on real components.

Each component's step was decided by its role, not by the component. Primer reaches the same place with one alias, `borderRadius.default`; Material maps each component's `container-shape` to a step.

Here is the review's form, before and after, with illustrative role names.

```css
/* Before: each control picks a step */
.button { border-radius: var(--radius-6); }
.input  { border-radius: var(--radius-4); }
.select { border-radius: var(--radius-8); }

/* After: one role, one edit */
:root { --radius-control: var(--radius-6); }
.button, .input, .select, .datepicker { border-radius: var(--radius-control); }
```

Making controls rounder takes four edits before, one after.

**Add roles for the groups that must change together (detail, control, container, overlay and full cover most libraries), point each at a scale step, and have components use only roles.** *Weight: strong.* Atlassian, Primer and Material all assign radius by job, and none leaves it to each component.

## Full and pill

Make "full" a very large fixed value such as `9999px`, never `50%`, and never mix it with small radii on the same box.

A Subscribe button is 160 by 44px with round ends. The obvious CSS is `border-radius: 50%`. See what each value draws.

The left button is an oval: CSS resolves a percentage against each axis, so every corner is an 80 by 22 ellipse. On the right, `9999px` is far too big, and that is the point. The CSS backgrounds specification says that when the radii on a side add up to more than its length, every radius is scaled down by the same factor, here to 22, half the height: a pill at any width.

That is why Primer, Polaris, Material Web and Radix ship full as `9999px`. The same rule has a sharp edge. A tab wants pill-round top corners and 8px bottom corners, and someone writes `9999px 9999px 8px 8px`.

The browser scales all four corners by the worst side's factor, about 0.0052, so the 8px corners land at 0.04px: square. Write the top corners as half the known height instead. Figma clamps each corner on its own, so the same values look right there ([radii and corner smoothing](../figma-and-code/where-figma-and-css-render-differently.md#radii-and-corner-smoothing)).

**Define `radius.full` as `9999px` on the web and as a 50% corner size on Android, and when a box needs one full side and one small side, write the full side as half the control height.** *Weight: strong.* The overlap rule is in the specification; the 50% difference is in each platform's documentation.

## Radius as a theme dial

When roundness is part of the brand, make it one multiplier over the scale rather than a second scale per theme.

The brand team's "a little softer" asks to change every corner in proportion. A theme could re-point each role a step up; Atlassian shipped that as experimental `shape-rounder` and `shape-roundest` themes in August 2025 and removed both in November, without giving a reason.

## What users notice

Nothing in the published research says one radius is easier to use than another; choose radius for consistency and meaning, and test the places where shape carries meaning.

The brand team says rounder means friendlier. The nearest evidence is psychology: Bar and Neta (2006) found people preferred curved objects to sharp-angled ones, and Bertamini and colleagues (2016) that the preference is for curvature itself. None of it tests interfaces, and no study read here varies radius alone on controls. GOV.UK proposed rounded buttons in October 2025 to look "friendlier", and took the change out of version 6 that December after community feedback.

Shape does carry meaning in places: a round checkbox reads as a radio (Radix and Nielsen Norman Group both warn), and a circular avatar means a person.

WCAG 2.2's target size criterion asks whether a 24 by 24 square fits inside the target, and rounded corners can leave too little room.

The name keeps its words; the number changes unit. The red line is the trap. Style Dictionary's native transforms (`size/remToDp`, `size/swift/remToCGFloat`) multiply the number by 16 whatever its unit, because they assume rem. A radius authored as 6px comes out as 96dp. A px-authored radius needs `size/dp` or a custom transform.

Then the unit, where radius parts company with spacing. Spacing goes out in rem so it grows with the reader's text ([spacing on three platforms](spacing-tokens-by-intent-part-2.md#one-model-three-platforms)); a corner is a shape, and in px it stays as drawn, matching Figma and the native platforms. Polaris, Primer and Atlassian ship radius in rem anyway, with no stated reason; Spectrum and Material ship px and dp.

**Store each radius as a DTCG `dimension` in px, build it with px-aware transforms (never the native `remTo*` ones), and keep radius in px in CSS so it matches Figma and the native platforms.** *Weight: contested.* Three large systems ship rem and two px; this toolkit's code standard (rule 54) keeps radii px.

## Radius in Figma variables

Put radius in two collections, primitives hidden and roles scoped to corner radius, give each role code syntax, and bind every corner field to a role.

The review's designers type radii into the corner field; variables make a role the only thing to pick.

```
Primitives (one mode, hidden from publishing, no scopes)
  radius/0  radius/2  radius/4  radius/6  radius/8  radius/12  radius/16  radius/9999

Shape (modes: Default, Rounder; scope: Corner radius)
  radius/detail     → radius/2   | radius/4
  radius/control    → radius/6   | radius/8
  radius/container  → radius/8   | radius/12
  radius/overlay    → radius/12  | radius/16
  radius/full       → radius/9999| radius/9999
```

The setup is the one [spacing in Figma variables](spacing-tokens-by-intent-part-2.md#spacing-in-figma-variables) walks through step by step, with three differences (Figma as of November 2026):

1. Name the role collection `Shape`, with modes `Default` and, if the brand needs one, `Rounder`.
2. Scope each role to Corner radius only, not Gap.
3. Bind in the appearance section's corner radius field; for a group or a sheet, open independent corners and bind each corner, leaving the square ones at `radius/0`.

One limit: independent corners cannot be changed on an instance, so a squared version of a component has to be a variant.

**Set up two collections, primitives hidden and unscoped, roles scoped to Corner radius with code syntax, and bind every corner of every component to a role, with a mode for any rounder theme.** *Weight: moderate.* Scopes and per-corner binding are Figma's documented API.

## Cheat sheet

| You have | Write instead |
|---|---|
| `radius.medium` as a primitive | `radius-6` or `radius-150`; the word goes on a role |
| Button 6, input 4, select 8 | One `radius.control` for all three |
| `border-radius: 50%` on a button | `radius.full` = `9999px` |
| `9999px 9999px 8px 8px` | Half the control height on top, 8 below |
| Card 16, padding 8, image 16 | Image `calc(16px - 8px)` = 8 |
| Focus ring layer at the button's radius | Radius plus offset; `outline` in code |
| `border-top-left-radius` on a side sheet | `border-start-start-radius` |
| Rounded sheet against the screen edge | Radius 0 on the edge side |
| Corner smoothing as a token | `.continuous` on iOS, `corner-shape` on the web |
| A second scale for a rounder brand | One factor, or one Rounder mode |

---

## The short version

Give radius a scale of six to ten steps named by value or multiplier, as spacing is, and put roles on top (detail, control, container, overlay, full) that components use exclusively (strong). Write full as 9999px on the web, never 50%, and never beside small corners on one box (strong).

An inner radius is the outer minus the padding, and a ring outside is the radius plus the offset (strong). Write per-corner radii with logical names, and square any side that meets the screen edge instead of shrinking radius by breakpoint (moderate to strong). Circles mean people (strong).

Store radius in px with px-aware transforms (contested; this toolkit keeps px), keep continuous corners out of tokens, and scope Figma roles to Corner radius (moderate). Audit first, rename before changing values, then turn the lint to error. Write down for engineering the role mapping, the nested and focus arithmetic, and which corners each sheet and group squares.
