# How a design system reaches the agent

Where a design-system team should put rules, reference and a portable snapshot so an agent finds each at the moment it needs it.

A developer asks an agent for a sign-in screen. The library has a described text field and a button, and a docs site generated from one record. The agent writes its own input with a raw grey, because nothing put any of that in front of it while it worked.

A well-described library ([Part 2](what-the-library-carries-for-an-agent.md)) and one record of it ([Part 3](design-system-docs-as-one-record.md)) are only half the job. The other half is the route: a context file, a server, a skill, a CLI, an `llms.txt` or a portable `DESIGN.md`.

## Where knowledge lives

Knowledge lives in three places, because rules, reference and a snapshot each fail in a different way.

Picture the team behind that sign-in screen writing everything it knows into one file at the root of the repository. Near the top go the five rules that matter: import from the library, never write a hex value. Below them go every component's props, every token's value and a description of the brand. The agent loads the whole file on every turn, and the five rules sit somewhere in the middle of it.

That file is doing three jobs at once. **Rules** are short imperative constraints, written by a person and always in context, so every line costs something on every turn. **Reference** is the bulk (component APIs, token values, usage), generated by a pipeline and fetched only when asked. A **snapshot** is one self-contained description of the visual identity, which travels anywhere and loads in full every time.

Here are the three side by side.

| Layer | What it holds | Where it lives | Loaded when | Written by |
|---|---|---|---|---|
| Rules | What never to do | `AGENTS.md`, `CLAUDE.md`, `SKILL.md` | Always, or on trigger | A person |
| Reference | Component APIs, token values, usage | An MCP server, a CLI, skills, schema files | On demand | A pipeline |
| Snapshot | The visual identity in one file | `DESIGN.md` | All at once | Generated, then tuned |

The last two columns are the point. Each layer is loaded on a different schedule and kept true by a different hand.

They also go wrong differently. Rules rot when nobody prunes them. Reference goes stale when the pipeline stops. A snapshot is out of date the moment it is written. The one enormous file inherits all three failures, loads everything every turn, and buries the handful of instructions that change behaviour.

Keep the three apart, and give each to whoever can keep it true: a person for your rules, a pipeline for your reference, a generator tuned by hand for your snapshot. **One file that tries to be all three costs on every turn and hides the few lines that matter.** The three-layer split is consensus among the vendors cited below; the table is a summary of their practice, not a published standard.

## Evidence on `AGENTS.md`

Two controlled studies answer different questions, one finding no general gain in success at higher cost and the other faster runs with correctness unmeasured, and both point at the same part to keep.

`AGENTS.md` is the cross-tool convention for repository rules. OpenAI released it in August 2025 and donated it to the Linux Foundation's Agentic AI Foundation on 9 December 2025. Codex, Cursor, Copilot, Gemini CLI and others read it, and the file nearest to the edited code wins.

The team's question is simple: does writing one make the agent better? The two studies split it in half.

[Gloaguen et al.](https://arxiv.org/abs/2602.11988), at ETH Zurich and LogicStar.ai, ran four frontier models three ways: with no context file, with a generated one and with a developer-written one. The tasks came from SWE-bench and from issues in repositories that ship their own files. Context files "do not generally improve task success rates", the paper found, and they raised inference cost by over 20 percent on average, across models, agents and both kinds of file.

Inside that result there is a useful split. The instructions in the files were well followed. The repository overviews, though popular and recommended by model providers, did not help. The paper's conclusion keeps a role for the files: specifying non-standard coding practices, with any attempt to improve performance evaluated before it is deployed.

[Lulla et al.](https://arxiv.org/abs/2601.20404) (ICSE JAWs 2026) asked about speed instead. They ran 124 real pull requests from 10 repositories twice with `gpt-5.2-codex`, with and without each repository's own `AGENTS.md`:

- median runtime fell 28.64 percent, from 98.57 to 70.34 seconds;
- median output tokens fell 16.58 percent, from 2,925 to 2,440.

It measured efficiency, not correctness. A file that makes an agent finish faster without making it finish correctly more often is consistent with both studies. Neither licenses "`AGENTS.md` is proven to help", and neither licenses "proven not to".

Here is the difference on a page, as an illustrative file. Most generated files open like this:

```markdown
## Repository layout
- src/components: React components
- src/tokens: design tokens
- src/pages: application screens
```

An agent can read every word of that from the folders themselves. These lines it can't:

```markdown
- Import buttons and fields from @acme/ui; never write a new one.
- Colours come from tokens. No hex values, even in a prototype.
```

Four traps follow from the studies:

- **The generated repository overview.** Usually the longest section, and the one found unhelpful.
- **The context file as documentation.** Anything discoverable from the code doesn't belong.
- **The auto-generated file.** The cheapest, and the setting with no success benefit.
- **The unbounded file.** Cost scales with length on every call.

Skills ration the same budget in steps. In [Anthropic's guidance](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), the name and description load at startup (about 100 tokens a skill), the body once the skill is triggered (under 500 lines), and bundled files only when referenced.

Even a well-written rule is advisory. The model may judge that it doesn't apply, so the step that must happen every time needs a hook; [Part 6](agent-workflow-enforcement.md) covers why a written step feels optional.

Write your rules by hand as imperative constraints, delete the repository overview, and turn anything deterministic into a lint rule or a check: zero tokens, and no question of compliance. **The lines that earn their tokens are the instructions the code cannot state about itself.** Both studies support that reading, though neither measured design-system work specifically.

## Reference on demand

Reference should load on demand for an established codebase: the one published head-to-head is decisive, and the vendors who measured agree on the direction.

Back to the sign-in screen. Atlassian ran that same task, building a login screen, four times with four kinds of context, and published what each cost:

| Context given to the agent | Guidance reached | Tokens | Time | Turns |
|---|---|---|---|---|
| None | about 5% | 4.20M | 6m 19s | 43 |
| Atlassian's MCP server | about 80% | 3.75M | 5m 01s | 35.1 |
| Atlassian's skill | about 80% | 4.43M | 5m 23s | 36 |
| Portable `DESIGN.md` | about 30% | 7.21M | 6m 46s | 45.3 |

Before reading on, look at the last row against the first. The portable file reached six times the guidance of no context, and still used 3.01M more tokens, 27 more seconds and about two more turns than giving the agent nothing.

Why would the file cost more than nothing? Atlassian named three causes.

- **All at once against on demand.** The file loads in full every turn, while a server answers a narrow question narrowly.
- **Portability forces compression, and compression cuts the useful part.** To stay portable the file was squeezed to 80KB (about 19,800 tokens), against roughly 2.5MB the server can draw on. In Atlassian's words, "we had to remove much of the usage guidance from our 50+ components", along with foundation guidance and a number of tokens.
- **A complete visual specification is a build recipe.** Given the full look of each component, agents re-created Atlassian's components rather than importing them.

The red block is the whole identity file, paid for on every turn whether the turn needs it or not. In the lower row the blue rules file stays small, and the green answers appear only on the turns that asked a question (the block sizes are illustrative, not measured).

Atlassian also had to ship a separate dark-mode file, because the format has no theming. It calls its own results not conclusive and publishes no run counts.

Two other measurements point the same way. Storybook reported, for the Reshaped library with its MCP docs against a baseline, 12.8 percent better code usage, 2.76 times faster and 27 percent fewer tokens. Those figures appear only in an image caption on Storybook's blog, with no tasks, models or run counts. Without the server, its agents generated their own components, typically with shadcn/ui and Tailwind.

> **Aside.** The [Reshaped experiment](https://github.com/storybookjs/ds-mcp-experiment-reshaped/discussions/1) started from an RFC (9 September 2025) in which Claude generated docs for every export of the package in about 26 minutes and for about $15. The RFC judged the result "not accurate, it's not consistent, and it's not exhaustive".

The remaining choice, a server or a CLI, is about a team's tooling rather than settled evidence. Atlassian's later CLI post reports an 8 percent cut against its own MCP server, in both session time (352 to 325 seconds) and tokens (218k to 201k), and CLI usage overtaking MCP usage. That is one team's data.

A preloaded file is like handing a new colleague the whole manual every morning; a server is the colleague down the hall who answers the question asked. Where the analogy stops: the colleague down the hall is only consulted if the agent thinks to ask, and that depends on its instructions, as [Part 5](what-keeps-an-agent-on-track.md) shows.

Serve your generated reference on demand from whatever your team already runs (a docs site's JSON, a server over it, or a CLI), and keep your rules file short. **An all-at-once file cost more than no context at all in the only head-to-head, so the reference is fetched, never preloaded.** The direction is consensus among the vendors who measured; the size of the effect rests on one team's test with no published run counts.

## Servers and `llms.txt`

Atlassian, Primer, Carbon and Spectrum ship design-system MCP servers, Polaris folds into Shopify's developer server, Salesforce ships skills only, and Fluent and GOV.UK ship none.

A team deciding what to build first usually looks at what the large systems shipped. An MCP server is a small program an agent can call with a narrow question (find the token for a disabled border, say) and get a narrow answer. Here is who serves what:

- **Atlassian's `@atlaskit/ads-mcp`**, in Early Access, runs locally or from a hosted endpoint. Its tools are `ads_plan`, search tools for components, tokens and icons (`ads_search_components`, `ads_search_tokens`), and axe-based accessibility tools such as `ads_analyze_a11y`. Its content is regenerated from ADS's structured content.
- **Primer's `@primer/mcp`** has nineteen tools, among them `list_components`, `get_component`, `find_tokens` ("by intent or value") and `lint_css`. It serves component APIs, examples, usage, accessibility guidelines and patterns. `list_patterns` and `get_pattern` tell the agent to prefer a scenario pattern (Create, Edit, Filter, View and others) when one fits. Its `PageLayout` is reachable only as a component.
- **Carbon** has a hosted server behind IBMid, serving "components, tokens, icons, guidance, and code". Its concepts page names the tools `code_audit`, `code_search`, `docs_search`, `get_charts` and `labs_search`.
- **Spectrum** ships `@react-spectrum/mcp`, agent skills and an `llms.txt`.
- **Polaris** folds its tooling into Shopify's `@shopify/dev-mcp`.
- **Salesforce** ships no server, only three agent skills that call the SLDS Linter.
- **Fluent and GOV.UK** have no official server that could be found.
- **Ant Design and shadcn/ui** ship servers too; what they serve for whole screens is in [Part 7](building-screens-with-an-agent.md).

An `llms.txt` is the lighter route: a plain file at a site's root that lists its pages for a model to follow. It is live at atlassian.design, carbondesignsystem.com and react-spectrum.adobe.com, and returns 404 at primer.style and at the GOV.UK design system. shadcn/ui publishes one too.

Figma's own MCP server reads the design side. `get_design_context` returns code for a selection (React and Tailwind by default), `get_variable_defs` lists the variables a selection uses, and `search_design_system` searches connected libraries. Atlassian's prototyping work, which collapsed its guidance into one file and moved the navigation into configuration, is told in [Part 7](building-screens-with-an-agent.md).

**A worked case: one toolkit's server.** The design-system toolkit took the on-demand route without a separate pipeline. Its docs site writes a JSON API beside its pages at build time, and `tools/system-mcp` is a read-only MCP server over that API, for one project at a time ([server README](https://github.com/javi-cuello/design-system-toolkit/blob/main/tools/system-mcp/README.md)).

Its tools are `overview`, `search`, `get_contract`, `get_component`, `get_tokens`, `get_changes`, `get_audit`, `get_screen_recipe`, `list_pages`, `read_page` and `validate`. The reference is whatever the site renders, so the server can't say something the docs don't. It had no `llms.txt` and no Markdown page variants. Whether an agent actually calls a loaded server depends on its instructions, a finding told in [Part 5](what-keeps-an-agent-on-track.md).

The `llms.txt` it lacks is a short file. Per [the proposal](https://llmstxt.org/), it has an H1, a blockquote summary, H2 sections of links and an `Optional` section, like this illustrative one:

```markdown
# Acme design system
> Components, tokens and usage guidance for Acme's web products.

## Components
- [Button](https://design.acme.example/button.md): actions and their variants

## Optional
- [Changelog](https://design.acme.example/changes.md)
```

If you have a docs site, add an `llms.txt` and Markdown variants of its pages: an afternoon's work, and it reaches agents that don't speak MCP. Build a server only once the reference is already generated, and put it over the docs' own data. **A server is worth building only over a record that is already generated, so the server can never say something the docs do not.** That the large systems ship servers is a fact; that a server should sit over the docs' own data is a judgement, made because it leaves one source to keep true.

## A portable `DESIGN.md`

A portable `DESIGN.md` is right for green-field work, a small team or a hand-off outside the team's infrastructure, where there is no coded library to import yet.

Take a team starting a new product with no component library in code. Atlassian's three objections don't bite here. There is nothing to import, so a build recipe is what the agent needs, and there is no server for the file to lose against.

`DESIGN.md` isn't trying to be a server. It is a portable, version-controllable description of an identity that works in any tool with nothing to run. Google Labs ships a CLI that lints, diffs and exports it, including a Tailwind v4 `@theme` block. The format is still pre-1.0, with no theming support in any release.

So the brownfield and green-field cases split cleanly. Atlassian's objections are brownfield objections: they assume a library the agent should import and a server that can answer narrowly. Where neither exists, a portable identity file with nothing to run is the simplest route that works.

There is a middle position. A CLI that answers narrow questions gets the on-demand property of a server and the nothing-to-run property of a file. Meta's Astryx (open-sourced in beta in June 2026, React and StyleX, around 13,000 internal apps) states the design: its API, docs and CLI are designed together, so a person and an AI assistant build the same way from the same reference. Its README names a CLI for "component docs, templates, scaffolding, themes, and codemods". It names no MCP server and no JSON manifest.

For green-field work, ship the snapshot with an explicit instruction to prefer existing components, and one file per theme until the format supports theming. **Choose the portable file when there is nothing to import yet, and the on-demand route once there is.** The split by brownfield and green-field is a reading of Atlassian's three objections, not a finding anyone tested.

## Cheat sheet

| For an agent to | Put it here | Not here |
|---|---|---|
| Follow the few rules the code cannot state | A short, hand-written rules file | A generated overview |
| Understand the repository layout | Nowhere; delete the overview | The top of `AGENTS.md` |
| Look up a component's API or a token | A server, CLI or skill over generated reference | A file loaded on every turn |
| Be blocked from a mistake | A lint rule or a check it runs (Parts 5 and 6) | Any context file |
| Work outside the team's infrastructure | A portable snapshot, or a CLI | A server with no fallback |
| Reach a docs site without MCP | An `llms.txt` and Markdown page variants | A 2MB dump |

## The short version

Keep your rules, reference and snapshots apart. Rules are short and hand-written and load every turn, so every line has to earn its cost. Reference is the bulk, generated, and fetched only when asked. A snapshot is one portable file for tools that can reach nothing else.

Of the two `AGENTS.md` studies, one found no general gain in task success at over 20 percent more cost, and the other found faster runs without checking correctness. Both point at the same thing to keep, the instructions the code can't state about itself, and the same thing to delete, the repository overview.

Serve your reference on demand: in Atlassian's test an all-at-once file cost more than no context at all, and a server or skill reached about 80 percent of the guidance. Atlassian, Primer, Carbon and Spectrum ship servers; an `llms.txt` is an afternoon's work for agents that don't speak MCP. A portable `DESIGN.md` still has a place for green-field work, with one file per theme until the format supports theming.
