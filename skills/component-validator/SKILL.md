# Component validator

**Version 2.30.10** — history in CHANGELOG.md.

A component is drawn once and built on one or more platforms, and each platform refuses some part of the drawing: the web has no centre stroke, SwiftUI has no line height, Compose adds 48 dp to anything tappable. Those refusals are documented by the platforms themselves, so they can be found in the Figma file before a line of code exists. When they are not, they surface as waivers written by a developer, in code, where the designer never sees them. This skill is the pass that looks first: it reads the component trees, applies one target's rule set, and puts each difference to the designer as a decision — **Figma** (redraw so the file says what the code will do), **code** (a known translation, written into the mapping), or **accept** (a named deviation with its reason).

It is stand-alone. It reads stored component trees, or the file itself where there is no snapshot, depends on no other skill's output, and its rule sets are sourced from the platform documentation that decides each case, not from any project. Where a project paid for a rule the reference may say so, as support; the rule is admitted by its source.

## Project context first

**The project's design system context document is authoritative.** In Claude Code it is a file in the working folder named by the project's `CLAUDE.md`; in claude.ai it arrives via Project knowledge or in the conversation. Hydrate from it: the target or targets, the layer-naming conventions the detectors key on (`Content`, `Wrapper`, `Focus ring`, `Slot`, `Hit area`), rulings that already accept a class for this project, and the component list in scope. Run discovery only for what it marks unresolved. A ruling produced by a run — "W5 on dividers is accepted; the code draws a 1 px border" — is written back to the document in the same turn where it is writable, otherwise emitted as a section to paste back. Where there is no document, the project's design-system README stands in.

## Step 0 · Which target

**Ask, unless the context document already says.** The three rule sets disagree on what is a finding: a `%` line height is clean on the web and a finding on iOS; a Hover state is a pseudo-class on the web, iPad-only on iOS, a state layer on Android; a 32 pt toolbar is fine on the web and under the hit target on both native platforms. Running the wrong target produces a confident report about the wrong platform.

One question, one answer per run: **web**, **ios**, or **android**. A library that ships to more than one is validated once per target, and the report is one table per target, because the designer's decision differs by platform (a centre stroke is *accept* on the web and *Figma* on Android). A framework target (MUI, shadcn, a native design system) is not a separate rule set: it is the platform set plus the framework's own constraints, which the agent adds by reading the framework's docs for the component at hand.

## Inputs

The engine reads `{ name, props, variants: [tree] }` per component, where a tree is what [`scripts/walk-figma.js`](scripts/walk-figma.js) returns. Two ways to get it, and **the stored snapshot is the default**:

- **From the project's snapshot (the default).** `--snapshot` reads the component trees the snapshot plugin stored, one `figma.json` per component folder. Figma is read once, by the plugin, and every output reads what was stored — a tool that reads the file live for data the snapshot already carries is a second reader of one fact, and the two disagree (toolkit-standard §D 5). The flag also tells the engine this shape's conventions: the plugin writes a field only where it differs from Figma's default and names truncation `truncate`, so an absent truncation is off, which is what it means there.
- **Live, for a file with no snapshot.** Run `walk-figma.js` through `figma_execute` in the library file, on the current page, or on the node ids in `const SCOPE = [ids];` prepended to it. Every lookup in it is the async form, because a library file runs under `documentAccess: dynamic-page` and the sync forms throw. Its output is not the snapshot plugin's shape (no boolean-flipped variants, no `compact`), so the two are not interchangeable as a store. It is small enough to paste per run, and it is what a file outside any project — a stranger's library, a file being evaluated — still gets. It stays because the skill runs alone, not because a project should use it.
- **From any other stored tree.** An export of another shape feeds as it is: the engine reads paints given as variable names or hex literals, an effect given as a style name, and takes line-height sources from a text-styles list (`--text-styles tokens.json`). Fields the trees lack leave the classes that need them silent, and the engine lists those under `silent` in its output so the report can say so. A class that raised a finding is never called silent, one present field never vouches for a missing one, and a class with two detectors where only one could run reads `(partly)`. Fields inside instances do not count as present, because the walk never enters an instance.

**The skill is the source of truth; a project wrapper knows only where its files live.** Resolving specs, choosing the target, printing: that is a project's script. What counts as a finding, which fields a class needs, how a stored shape is read: that is the engine, and a wrapper that re-derives any of it will drift the first time the engine changes. Written after the first wrapper did exactly that — it carried its own paint mapping, its own line-height lookup and a hand-typed list of silent classes, all three stale within a day.

There is no third path where the agent reads the file and decides by eye. A class it can detect, it detects by script, because a hand-read pass varies between runs and misses the twelfth component.

## Running it

```sh
node scripts/validate.mjs --target web|ios|android [--text-styles tokens.json] [--states '{"axis":…,"options":[…]}'] [--snapshot] components.json
```

`--snapshot` says the trees are the snapshot plugin's, which writes a field only where it differs from Figma's default, so an absent truncation is read as none; `--states` is the state axis below.

Exit 1 when anything was found; output is `{ target, silent, findings }` — `silent` the class ids the input cannot show, `findings` an array of `{ class, component, layer, detail, align, variants }`, one per decision, identical findings collapsed across variants. A finding also carries `key` (`<class>|<layer or shared cause>`), `lands` (figma / both / code / accept, read from its advice) and, where the target has a name for it, `expected`, so a row can render as a comparison rather than a sentence. Findings collapse on their advice, not their detail: one decision per layer per advice, with every particular it covers kept, while a layer that raises two different questions still gets two rows.

**An instance is visited, never entered.** What is inside it belongs to its main component and is audited under that name; filing it against every parent that places the component sends a designer looking for a layer that is not there. A rule sees the instance node itself only when it declares `onInstance`, and those rules are about the placement — absolute position, icon size, MU8's square artboard. Smoothing, strokes, fills, effects and line heights inherited from the main component are not the parent's findings.

**The state axis is the library's, passed in.** Callers pass `states: { axis, options }`, read by `contract.validatorStates` from the library's `stateAxis` and `optionOrder` (the CLI takes `--states`). W7's axis check, WT1, I12 and the hit-target rules read that axis; with none recorded they stay silent rather than guess, and advice says "the state axis", never one library's name for it.

Then:

1. **Judge each finding against the context document.** A class the project has ruled accepted is not reported again; it is listed once under "already ruled" with the ruling's date. A detector hit is not a defect until the agent has read the layer: a `Focus ring` clipped on purpose because the list scrolls is a ruling, not a bug; a `Hover` variant on an iOS library aimed at iPad is a choice.
2. **Report in the numbered table** `# · Component · Layer · Class · What · Align (Figma / code / accept)`, worst first: classes that change the component's API (states as booleans, W7 / I12 / A12) and structure the code must reshape (W1–W4, I8, A15), then values (strokes, text, effects, colour), then content. A reader should be able to take the table to the designer as is.
3. **Put the choice to the designer before anything is built.** Each row ends in one word — *Figma*, *code*, *accept* — and until the designer has chosen, nothing under that component starts in code on that target.
4. **Record the rulings** in the context document, keyed by class id and target, so the next run stays quiet about them and a later waiver can cite the ruling rather than invent a reason.

The class definitions — what Figma allows, what the platform does with its source, the alignment, the signal — are one file per target: [`references/web.md`](references/web.md), [`references/ios.md`](references/ios.md), [`references/android.md`](references/android.md), plus [`references/mui.md`](references/mui.md) for the framework layer that sits on top of the web target. Read the entry before judging a finding you have not seen; the engine names the class, the reference says why it matters and where that is written.

**A rule's predicate must match its reference's Detect line, and an audit of the two found five that did not.** The Detect line is the specification; the code is the implementation, and when they disagree the reference is right unless its own mechanism paragraph says otherwise. Five classes were reporting things that were not true — `W3` fired on a layer named "Optional" and on a single menu row, `W2` on every row of an input-like component rather than the field, `A14` on "Icon button", `I7` on fill siblings holding no text, `A8` on a spread shadow Compose can draw — and four more were dead while reading as clean. **Changing a shared detector changes every target that calls it**: fixing `blurs` for the web silently removed the signal iOS and Android both name first in their Detect lines. Each of the nine now has a case.

## Translations, for a developer

The same knowledge read the other way. `translations(components, target)` returns what the target builds differently from the drawing where nothing needs deciding — a focus ring drawn as a layer is an `outline` on `:focus-visible`, an inside stroke is a border inside `border-box`, a `State` axis is pseudo-classes, `Role` is renamed `variant` — as `{ id, component, figma, code, why, layers }`, one row per rule and component (Markdown in each cell) across every variant. It is for a component's documentation page, never for the audit: `validate()` asks the designer a question, `translations()` tells the developer an answer. Where a class covers the same layer (a clipped ring is W4, an outside stroke W5), the class speaks and the translation stays quiet. Entries and sources: *Translations* in [`references/web.md`](references/web.md). Web only so far; the other targets return none. A caller that uses a framework passes it and its component map to `translations()` and `validate()` alike: a docs build that passed the platform target alone left the framework's code-only findings in neither the audit nor the docs. The docs site calls it, and a note it should carry is added here, never in the page that shows it.

## What the engine cannot see, and who looks

Stated so the report does not read as complete when it is not:

- **Screen-level classes** (iOS safe areas, I14) are not in a component tree. The report says so rather than claiming them.
- **The iOS and Android tables have never fired on a project**, because every registered library so far records `codeTarget: web`. They are tested against fixtures and raise findings when run, but no real library has been validated for either, so a first run there is a first walk.
- **Whether a wrapper is needed** (W1), whether five identical rows are a list or the design (W12), whether a fixed width is a grid track (W8): the engine reports the shape, the agent decides.
- **Image scale modes** (W14), **mask layers** (W15), **corner smoothing** (W13, I2) and the **effect kinds** the blur and shadow classes key on reach the snapshot from plugin 0.33.0. An older stored snapshot lacks them and leaves those classes silent — which the report says, rather than reading as clean.
- **The reverse direction** — a state or value the code offers that Figma never drew — is not visible from Figma at all. A parity check's coverage gate catches it after the build; there is no pre-build check for what has not been designed.
- **A framework's own constraints** (a `TextField` that owns its adornment slots, a Material component that sets its own minimum size) are read by the agent from the framework's documentation for the component at hand, on top of the platform set.

## Called by other skills

`figma-components-audit` may name this skill as an optional stage after its own scan, scoped to the same components, when the project has a code target. `figma-project-audit` runs it for the target the library's settings name as `codeTarget`. Its findings join the fix queue under their class ids in the *Decide* section: none is a safe automatic fix, because each is a choice between Figma, code and accept. The audit dashboard's *Audit* runs it too, for the recorded target, over the LIVE file: the service runs the snapshot plugin's own file headless through the bridge (`plugins/design-system-snapshot/code.js`, 0.45.0), which walks every component set into the very shape the store records, and resolves those specs exactly as it resolves stored ones — an audit is about the present, a snapshot about a stored state (toolkit-standard §D 5), and until 2026-09-22 this stage read the snapshot while its three siblings read Figma, so a shadow removed at lunch was on the Web build board at night; its judgement pass may drop a class only where a ruling names it, since every finding here is a decision for the maintainer and a judge that dismisses "deliberate-looking" strokes reversed itself between two runs of one file. The docs site imports `validate()` and `translations()` for each component's Implementation section, over the snapshot, because a documentation page describes a stored state and must be reproducible from it. Other skills name this one to run; none reads its files.

## Writing to the project's record

When the project keeps an audit record (`<project>/audit/<fileKey>.json`, one per library, because a library is a Figma file and two files have two runs, named in the context document's registry), a run writes its findings there as well as reporting them, so the dashboard shows them beside the audits' rows. File them through the record's one writer, `POST /rows` on the project's dashboard service or `node tools/figma-audit/rows.mjs --data <record>` when no service runs, never by hand: `{ owner: "component-validator", target, fileKey, full, scope, findings }`, one finding per class hit with `rule` the class id, `check` the engine's `detail` as given, `key` as given (the writer matches on it before the wording), `where` the component and bucket 3. **A run closes only rows it owns, for the target it ran**: `target` is part of a row's identity, so a web run never closes an iOS row on the same component, and only a run with `full: true` over `scope` closes the classes it no longer raises there. A ruling goes to the context document, never onto the row.

## Adding a target

A target is one reference file and one rule table in `scripts/validate.mjs`, over the same tree shape, with its own cases. Every class enters with the platform source that decides it — the specification, the API reference, the platform's guidelines — and a signal the tree can show; a class with a project incident and no source is a candidate, noted in the reference's *Not found* list until the source is found. Class ids are per target (`W`, `I`, `A`); do not align them across targets.
