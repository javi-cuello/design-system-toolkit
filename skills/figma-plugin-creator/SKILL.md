# figma-plugin-creator

**Version 1.12.0** — history in CHANGELOG.md.

Creates plugins that meet `standards/skill-standard.md` §B (toolkit repo) and audits existing ones. No build step: hand-written `code.js` + single-file `ui.html`. In Claude Code, work inside the toolkit repo (`plugins/<name>/`); follow the repo's CLAUDE.md. In claude.ai, produce the folder as deliverables.

## Scaffold a new plugin
1. Ask (or infer from the request): plugin name, one-line purpose, does it need a UI, does it re-run on nodes (→ relaunchButtons + `setRelaunchData`), does it call the network (→ real `allowedDomains`, else `["none"]`), what does it store (→ README "Data this plugin stores").
2. Write the folder with `node scripts/scaffold.mjs <folder> --name "…" --purpose "…" --storage "…"`: it writes **all seven** templates in `assets/` (`manifest.json.tpl`, `code.js.tpl`, `ui.html.tpl`, `package.json.tpl`, `tsconfig.json.tpl`, `CHANGELOG.md.tpl`, `README.md.tpl`), filling `{{name}}`, `{{slug}}` (the folder name, as the manifest `id`), `{{purpose}}`, `{{storage}}`, `{{date}}` and `{{standard}}` (the current `skill-standard.md` version, per skill-standard §B 8 — the header stamp records what the plugin was last audited against and is expected to lag thereafter), at version `0.1.0`; each answer is one line, escaped for the file it lands in. The ui.html template inlines the ui-base block from `assets/ui-base.css` verbatim, CAUTION comment included (both are written from `plugins/_shared/ui-base.css` by `node plugins/_shared/sync.mjs`: to update the baseline, edit that file and run it) — that comment is where a plugin author meets the bare-selector collision trap, so keep it. The templates alone satisfy the conformance check, and the script refuses a placeholder no answer fills, so nothing is left to patch by hand; never copy them by hand (toolkit-standard §D 23). The answers in step 1 stay the agent's, and so do the changes they lead to (steps 1 and 5): real `allowedDomains`, relaunch data, the window's size, and for a plugin with no UI, dropping `ui.html`, the manifest's `ui` and the `showUI` call.
3. Non-negotiable manifest fields: `documentAccess: "dynamic-page"`, `networkAccess`, `editorType`, `id` (the folder name; a development plugin without one gets a fresh id on every import and loses its relaunch data and `pluginData` — never changed after storage exists, per skill-standard §B 2). Never `enableProposedApi`.
4. Generated code is async-by-default (…Async APIs only), sets `figma.skipInvisibleInstanceChildren = true` before traversal, wraps async work in try/catch → `figma.notify(msg, {error:true})`, and calls `figma.closePlugin()` on no-UI completion.
5. If the plugin's UI fetches external data: read `references/network-fetch-patterns.md` FIRST. Default to jsdelivr, not unpkg (unpkg rejects null-origin requests outright — confirmed, not theoretical); pin an exact version; if it lazy-loads many items into a grid/list, inline `assets/fetch-queue.js` (bounded concurrency + retry + honest-failure state; not one of the seven templates, copied only when needed) rather than reinventing it.
6. Every scaffold includes `tsconfig.json` and `// @ts-check` as the second line of `code.js`, right after the version header — no-build type-checking, required by **skill-standard §B 1** and checked by this skill's `references/conformance-checklist.md` §4. Both come from the templates; verify rather than add.
7. Finish: run the conformance check below on the new folder; remind the user to import via Figma → Plugins → Development → Import plugin from manifest.

## Conformance check (existing plugin)
Run `references/conformance-checklist.md` top to bottom: manifest fields → banned-sync-API grep (regex in the reference; **only add `documentAccess` after the grep is clean**) → networkAccess vs actual fetch calls (and, if it fetches from a CDN in `ui.html`, cross-check against `references/network-fetch-patterns.md` — unpkg-only with no jsdelivr fallback is a needs-decision finding) → `tsconfig.json` present + `// @ts-check` as code.js's second line (auto-fixable: copy from `assets/tsconfig.json.tpl`) → version/changelog/README presence → settings hygiene: for every `settings.<field>`, confirm it drives the property its name claims to — a value flowing into a decorative/chrome property unrelated to its stated purpose (e.g. an icon-import setting silently driving a boundary-stroke property) is a needs-decision finding, not a style nit → ui-base collision check on plugins with >2 bespoke controls: for each bespoke button/input/select class, verify it explicitly sets `height` + `box-sizing:border-box` — if not, ui-base's bare element selectors are silently supplying that value by accident; make it explicit even when the inherited value already matches — this ALSO applies to :disabled/:hover/:focus states: if ui-base already defines the correct state treatment on a bare selector (e.g. Figma's real disabled tokens), check any more-specific plugin rule for that same state isn't silently shadowing it with something worse → ui-base (MANDATORY: inline the block if absent, re-inline on drift; reconcile by stripping plugin CSS that duplicates base control styling while keeping plugin-specific rules; finish with a visual retest in light and dark theme). Report findings classified `auto-fixable / needs-decision / manual`, fix only with approval, and never modify plugin logic during conformance — structure, manifest, metadata, and UI chrome only.

## Diagnosing "the UI shows nothing / is stuck / looks broken"
Before proposing code changes: **ask for the actual browser console** (right-click the plugin UI → Inspect → Console → reproduce → copy the red lines). A CORS rejection, a thrown exception, and stale/uninstalled code all LOOK IDENTICAL from outside the browser — remote diagnostics (reading `pluginData`, re-testing logic, checking deployment) cannot see any of them directly and can burn a long session chasing the wrong one. See `references/network-fetch-patterns.md` for the confirmed unpkg-rejects/ jsdelivr-works case specifically. Separately: if a live diagnostic script (e.g. a bridge/dev-tools plugin) reads a DIFFERENT plugin's `pluginData` and finds it empty, that is not evidence the target plugin's storage is empty — `pluginData` is scoped per-plugin-id; only that plugin's own code can see its own data.

## Constraints encoded (don't re-derive)
- ui.html is loaded as one document: relative `<link>` to a local css does not resolve — the baseline must be inlined between the ui-base markers.
- Colour only from injected `--figma-color-*` (requires `themeColors: true`); metrics from ui-base (Inter 11px, 32px buttons, 30px inputs, radii 2/6px).
- Storage: clientStorage 5 MB/plugin; pluginData/sharedPluginData 100 kB/entry (enforced). Manifest has no version field → package.json is the source of truth.
- A changed manifest requires re-import in Figma; "run last plugin" is not enough.
