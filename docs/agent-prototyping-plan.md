# Plan: agent prototyping in code and Figma

**Goal.** An agent builds whole screens from a project's own components, tokens and screen conventions, in code and in Figma, and a screen moves between the two without being redrawn. Written 2026-11-04 from [knowledge/code/agent-prototyping.md](../knowledge/code/agent-prototyping.md) and the research pieces *Prototyping with a design system's real components* and *Making a design system usable by AI agents*.

**Where we start.** Component contracts are derived from Figma and from code (`tools/component-contract`), drawn back into Figma (`to-figma.mjs`) and generated as CSS and markup (`to-code.mjs`, `to-markup.mjs`). `tools/docs-mcp` serves contracts and tokens to agents, and its `validate` checks what they write. The parity loop measures code against Figma, screens included. What is missing is everything above one component: screen knowledge, a prototyping workflow, and a screen-level bridge between the two sides.

**What the research adds and where we go past it.** Vallaure's two routes (Storybook MCP, or a custom MCP) and her handoff (an unmerged prototype branch, CI gates, a person decides) cover the code side for components. Atlassian's lessons: one parsed guidelines file, templates, and structured config over prose. Nobody in the research covers screen conventions served to an agent, or a screen that round-trips between Figma and code. Phases 3 and 5 are new ground, so each one starts with a trial before anything is built on it.

## Phase 1 — Components an agent cannot get wrong

The component layer is strong for people and for parity, and weaker for agents. Each step closes a place where an agent still guesses.

| # | Step | Why | Owner | Done when |
|---|---|---|---|---|
| 1.1 | `validate` checks imports: every component comes from the project's package or `paths.components`, and nothing is copied in | The import test, made a script; today `validate` checks values and raw HTML, not where components come from | `tools/docs-mcp/validate.mjs` | A test feeds a copied `button.tsx` and a lookalike, and both fail |
| 1.2 | `validate` runs at the gate, a pre-push hook in each project and in CI where one exists | A check the agent may skip is advice (the SLDS warning; Atlassian's models claimed correct code that wasn't) | project-check, `tools/claude-hooks` | blackbook and suiteify refuse a push with a raw `<button>` |
| 1.3 | A static manifest in the repo: `get_contract`'s data for every component, generated by the snapshot, with no server needed | Agents without MCP, small systems, CI. Generated, never written | `tools/snapshot` deliver | `--check` diffs it like tokens; an agent finds a prop with `grep` |
| 1.4 | Turn on Storybook's `componentsManifest` and paste its agent snippet into blackbook; add `@storybook/addon-mcp` to suiteify | Route 1 costs one line each | project config | `docs-list` returns the library in both |
| 1.5 | Composition in the contract, served: a slot's preferred instances and the components each one accepts | Screen building is mostly "what goes inside what"; the contract already stores slot settings | `component-contract`, `get_contract` | `get_contract Card` lists what its slots take |
| 1.6 | Intent coverage: Usage, Don't (each with an alternative) and Code gen notes on every public component, measured on the readiness page | The guidance agents retrieve against; the audit raises a row but nothing shows coverage | `docs-site` readiness, figma-component-descriptions | Each project's coverage is a number with its gaps listed |
| 1.7 | Code Connect generated from contracts and mappings, so Figma's own MCP returns the real import instead of Tailwind | Figma's agent and `get_design_context` guess without it ("the model is guessing"); the toolkit already knows each import | `component-contract` (new `to-code-connect.mjs`) | `get_design_context` on a blackbook frame returns `@/design-system` imports. Needs a Dev or Full seat on Organization or Enterprise; confirm the plan first |
| 1.8 | A behavioural baseline: ten product tasks that never name a component, run with and without context, scored by `validate` | Readiness is measured by agents, not files; it gives every later phase a before and after | `tools/skill-evals` | One scored table per project, kept with its date |

**Order:** 1.1 and 1.2 first, since they make the rest checkable. Then 1.4 (cheap), 1.3, 1.5, 1.6, 1.8. Step 1.7 waits on the seat check.

## Phase 2 — Screen knowledge an agent can read

An agent that knows every component still lays out a screen generically. This phase gives it the project's own conventions.

| # | Step | Why | Owner | Done when |
|---|---|---|---|---|
| 2.1 | Trial first: from blackbook's built screens (`src/screens`, the Screens file), list what repeats (page shells, list and detail, forms, empty states, and the spacing between regions) | Find out whether conventions can be derived before deciding how to store them | this plan | A written list of patterns, each with the screens it appears in |
| 2.2 | Screen recipes in the context document: per pattern, its regions, the components in each, the spacing tokens between them, and the states it must cover (empty, loading, error) | A project's truth lives in its context document (§D 12); the generic version is `knowledge/ui/patterns` | figma-context-capture | blackbook's recipes cover every screen in 2.1 |
| 2.3 | Templates: one per recipe, as a real story in code and a real frame of library instances in Figma | Atlassian's Fast and Full templates cut errors to "nearly zero"; a template is a recipe an agent can copy | project, drawn by phase 3's tools | Each recipe has both, held to parity |
| 2.4 | `docs-mcp` serves them: `list_patterns`, `get_pattern` (the recipe, its template on both sides, its states), and screens from the snapshot | On demand, like Primer's `get_pattern`; the snapshot already stores screens, but the site does not show them | `docs-site`, `docs-mcp` | An agent asked for "a settings screen" fetches the recipe before writing |
| 2.5 | Structured config where prose fails: navigation, the shell and the workspace switcher as data the template reads | "Structured configuration beats open-ended prompting" (Atlassian) | project | Changing the logo or a nav item edits config, not markup |

## Phase 3 — Prototyping in code

| # | Step | Why | Owner | Done when |
|---|---|---|---|---|
| 3.1 | A prototype mode in frontend-build: compose a screen from a recipe, only library components, and a receipt of what was used and what was invented, with each invented item marked in code | Vallaure's prompt, made a skill; the receipt turns gaps into backlog | frontend-build (one owner for building UI, §D 1) | A run on a new screen yields a story and a receipt |
| 3.2 | Flows as stories in a `Prototypes/` group: local state, `linkTo`, play functions, mocked data | Storybook already carries a click-through, and every part is the shipping one | frontend-build, project | One three-step blackbook flow is a story |
| 3.3 | The handoff: prototypes on a branch that never merges; accepted ones rebuilt on a feature branch behind 1.2's gate | Keeps throwaway code out of a repo that deploys `main` to production | frontend-build, project CLAUDE.md | Written into blackbook's working rules; the push hook refuses a merge from a `proto/` branch |
| 3.4 | Sharing: Chromatic per branch, linking to the flow story's full-screen view | A reviewer opens it without Storybook's chrome | project | One link opened while logged out |

## Phase 4 — Prototyping in Figma

| # | Step | Why | Owner | Done when |
|---|---|---|---|---|
| 4.1 | Trial first: compose one blackbook screen from a recipe on a scratch page, through `use_figma` and through Figma Console, using library instances and variables only | `use_figma` is beta and its limits changed in October; pick the route on evidence | this plan | Both routes tried, one chosen, limits written down |
| 4.2 | A Figma prototype skill: read the recipe and contracts (docs-mcp), place instances with their props, bind spacing, wire prototype reactions for a flow, and write the same receipt as 3.1 | The same job as 3.1 on the other surface; it shares the receipt format | a new `figma-screen-compose` skill, or a mode of an existing one (decide at 4.1) | A screen and a two-step flow on the scratch page, receipt attached |
| 4.3 | Check what it drew: only instances (no detached frames), every value bound, invented parts marked | The Figma counterpart of `validate`; the components audit's scanner already has most of these checks | figma-components-audit scanner, scoped to a frame | Running it on 4.2's screen reports what was invented and nothing else |

## Phase 5 — The seamless transition

The new ground. Today a component goes both ways; a screen goes neither way except through parity measuring.

| # | Step | Why | Owner | Done when |
|---|---|---|---|---|
| 5.1 | Figma screen → code: from a frame of library instances, write the screen's markup, each instance as its component with its props (to-markup's imports, applied to a screen's tree), and the mapping `propose.mjs` already drafts | A Figma concept becomes a code prototype without retyping | `component-contract` (`screen-to-markup`) | A blackbook screen from the Screens file renders and passes parity first time |
| 5.2 | Code screen → Figma: from a rendered story, draw the screen as library instances with their props (from-code's reading of each part plus to-figma's instance drawing), never flat layers | `generate_figma_design` flattens; designers need instances they can edit | `component-contract` (`screen-to-figma`) | A code prototype drawn into the scratch file is all instances, and the audit check from 4.3 is clean |
| 5.3 | The round trip as a test: code → Figma → code, and Figma → code → Figma, with parity measuring each leg | A transition is seamless only if a round trip changes nothing | `tools/parity` | Zero differences on two blackbook screens, both directions |
| 5.4 | What cannot cross is named: data, behaviour and states Figma does not draw, reported as gaps on each leg, never guessed (§D 15) | Honest output is the difference between seamless and silently lossy | as 5.1 and 5.2 | Each leg's report lists what it left out |

## Measures

- Phase 1.8's behavioural table, re-run at the end of each phase. Success: fewer invented components and props, and fewer raw values, against the same tasks.
- The receipt counts from phases 3 and 4. Invented items should fall as recipes and templates grow.
- The round-trip difference count from phase 5.

## Open questions

- 1.7 needs a Figma plan and seat that allow Code Connect. Which projects have one?
- Suiteify's code is a read-only clone. Its prototypes live in a separate repo on the published package, so 1.2 and 3.3 apply there, not to the clone.
- Figma Make kits with a package are a third surface. Parked until Vallaure's Part 3 (10 November) and a trial show they import the package.
